## 一、症状（来自 Log + 用户描述）

| 现象 | 用户陈述 / Log 证据 |
|---|---|
| **WASD 与 CameraFwd 完全瘫痪** | 用户："只能 W 向 CharacterFwd, CameraFwd 失效" |
| **角色不沿 world 输入移动** | Log 显示 `world=(-0.51,-0.86)` 但角色 `charFwd=(0.00,1.00)` 始终不变 |

## 二、根因（一句话）

> **`PlayerLocomotionState.OnEnter` 把 `m_lastHadInput` 无条件重置为 `false`；玩家从 Action 返回 Locomotion 时若方向键仍按住，下一帧 `hasInput=true`、`wasHadInput=false` → DetectRequestedState 误判为 press 边沿 → 再次 FIRE WalkStart/RunStart → 切回 ActionState → 永远卡在"起步段重播"循环，永远到不了 Move Loop（`MoveByLocomotionIntent` 永不执行）。**

### 2.1 帧序复盘（按 Log）

```
帧 47          : Locomotion.OnEnter → m_lastHadInput=false
帧 48          : OnLogicUpdate → Detect 见 hasInput=true (W 按住) + wasHadInput=false
                 → press 边沿 → WalkStart FIRE → ArmPendingAction → Change<ActionState>
帧 48–88       : ActionState 播 Walk_Start_Anim (~40 frame ≈ 0.67s)
                 期间 MoveByLocomotionIntent 不跑；位移完全由 Action 的 RootMotion / MotionProfile 驱动
帧 89          : Action 结束 → Change<LocomotionState>
帧 89          : OnEnter 再次重置 m_lastHadInput=false  ★ BUG
帧 90          : OnLogicUpdate → 同样的 press 边沿误判 → WalkStart FIRE → Action
…              : 13 次循环……
```

### 2.2 为什么"只看到 CharacterFwd 移动"

- Walk_Start_Anim 是个固定方向的起步动画（RootMotion 向 CharacterForward）
- 每次播放时 `MotionExecutor.Begin` **快照 burstFaceDir** 为角色当前 forward
- ASD / Camera 旋转改变 `MovementIntent` 的 world 向量，但**永远进不到 Locomotion 的 `MoveByLocomotionIntent`**（被 SKIP_MOVE 跳过）
- → 玩家看到的就是"反复起步、始终朝最初的 forward"

### 2.3 为什么 158.2 没暴露

158.2 时 press 边沿映射到 **合一 `RunStart`（Id=7）**，许多用户 Profile **没注册** RunStart Binding → Resolver 一级降级 → `DowngradedFromLogicLayer=true` → 早期 return false → 不触发循环。
159.1 L0 用户**正确配齐**了 WalkStart/RunStart Binding，反而触发了这个之前被隐藏的 OnEnter 重置 bug。

## 三、修复方案

### 3.1 单点 Fix（推荐）

`PlayerLocomotionState.OnEnter` 把 `m_lastHadInput` 与 `m_lastWantsRun` 从"无条件清 false"改为"**同步当前真实输入状态**"。

```csharp
protected override void OnEnter(Player player)
{
    RefreshLocomotionTags(player);
    m_turnResolver.ClearLock();
    player.SetTurnInfo(default);
    player.ClearGraphContextAction("enter-locomotion");

    // 163.1 FIX：从真实输入采样，避免"刚从 Action 返回 Locomotion 把仍按住的方向键当作 press 边沿"
    // 旧逻辑（强制 m_lastHadInput=false）会让 Action 结束的下一帧重新触发 WalkStart/RunStart → 死循环
    m_lastHadInput  = player.HasMovementIntent;
    m_lastWantsRun  = player.WantsRun;
    m_pivotCooldownRemaining = 0f;
}
```

### 3.2 语义复核（fix 后的 4 个核心场景）

| 场景 | OnEnter 后 m_lastHadInput | 下一帧表现 | 期望 |
|---|---|---|---|
| 游戏首次进 Locomotion（无输入）| `false` | hasInput=false → Idle 持续 | ✅ |
| 游戏首次进 Locomotion（W 已按住）| `true` | hasInput=true, wasHadInput=true → **非 press 边沿** → 走 Move Loop（既往合理）| ✅ |
| **Action 结束回归（W 持续按住，关键 fix 场景）** | `true` | **非 press 边沿** → 不再 FIRE WalkStart → 进入 Move Loop / MoveByLocomotionIntent | ✅ |
| Action 结束回归（动作期间已松手）| `false` | hasInput=false → Idle；后续若按 W → press 边沿 → WalkStart FIRE | ✅ |

### 3.3 为什么不动 DetectRequestedState

DetectRequestedState 的逻辑本身正确——press 边沿 = "上一帧无输入 + 本帧有输入"。问题在于 `m_lastHadInput` 的初始化错误地丢弃了"我是不是从 Action 回来"的语义。修 OnEnter 比改 Detect 干净得多。

### 3.4 m_pivotCooldownRemaining 仍清零

保留 `m_pivotCooldownRemaining = 0f` 不变。Turn180 Action 的播放时长一般 ≥ 0.4s（PivotReentrySeconds），自然就过了冷却；额外清零无副作用。

## 十、根因衍生：未来防御性建议

1. **edge-detection 模式的通用陷阱**：任何依赖 `m_lastX` 缓存做边沿判断的逻辑，状态切换时**必须**同步缓存而非清零。
2. **建议把 latch 同步移到一个 `SyncInputLatchOnEnter` 方法**，标注用途，避免未来其他状态 OnEnter 复制错误模式。
3. 后续若引入 LockOn / Crouch 等额外输入维度，同样原则适用。
