## 4 个 Bug 的代码事实诊断

### Bug #1 + #4：**双时钟撕裂**（最严重）

**核心证据**（`ActionDataSO.cs:146-159`）：
```csharp
public float ResolveAnimWallClockSeconds()
{
    if (MainClip != null)
    {
        if (Duration > 0.001f)
            return MainClip.length / Mathf.Max(0.01f, AnimSpeed);  // ★ 跟 else 同

```

`if (Duration > 0.001f)` 的 **双分支返回完全相同** → **Duration 字段对动画墙钟毫无影响**。

**双时钟**：
| 时钟                     | 数据                                 |
| ------------------------ | ------------------------------------ |
| 逻辑（nt / actionEnded） | `m_baseDuration = Duration` 优先     |
| 动画（Clip 播放）        | `MainClip.length / AnimSpeed` 自由播 |

**用户感受**：
- Duration=0.5、Clip=1.5、AnimSpeed=1 → nt 在 0.5s 到 1 → ActionEnded → 切回 Idle → 但 Clip 才播 33% → **"闪一下回 Idle"** ←  #2 落地现象

## 一、4 个 Bug 的代码事实定位

### Bug #1 + #4 —— 动作时序的双重时钟（位移播完才动 / Duration 形同虚设）

#### 关键代码

**`ActionDataSO.cs:146-168`** —— Duration 与 Clip 长度的 3 个 Resolver：

```csharp
public float ResolveAnimWallClockSeconds()
{
    if (MainClip != null)
    {
        if (Duration > 0.001f)
            return MainClip.length / Mathf.Max(0.01f, AnimSpeed);  // ★ 跟 else 同
        return MainClip.length / Mathf.Max(0.01f, AnimSpeed);
    }
    return ActionTimeAuthority.ResolveAuthoredLogicDurationSeconds(this);
}

public float ResolveLogicalDurationSeconds() =>
    ActionTimeAuthority.ResolveAuthoredLogicDurationSeconds(this);  // 优先 Duration，否则 Clip 墙钟

public float ResolveMotionDurationSeconds() => ResolveLogicalDurationSeconds();
```

⚠️ **`ResolveAnimWallClockSeconds` 内 `if (Duration > 0.001f)` 双分支返回完全相同**，等价于：**Duration 字段对动画墙钟毫无影响**。

**`PlayerActionState.cs:46`** —— Action 时钟：

```csharp
m_baseDuration = ResolveActionDuration(player, m_action);  // → MotionDurationResolver.Resolve
// 内部走 ResolveLogicalDurationSeconds = 优先 Duration，否则 Clip ÷ AnimSpeed
```

**`PlayerActionState.cs:122-170`** —— 推进与退出：

```csharp
m_elapsed += dt;
var nt = m_baseDuration > 0.0001f ? Mathf.Clamp01(m_elapsed / m_baseDuration) : 1f;
...
var actionEnded = nt >= 0.9999f;  // Action 终止：m_elapsed ≥ Duration
```

#### 双时钟撕裂

| 时钟 | 数据 | 用途 |
|---|---|---|
| **逻辑时钟** | `m_baseDuration = ResolveLogicalDuration`（优先 Duration） | `nt`、Phase Tag、HitFrame、退出条件 |
| **动画时钟** | `MainClip.length / AnimSpeed`（Animator 自由播） | Clip 的视觉播放 |

二者**不互锁**。设想资产：
- `MainClip.length = 1.5s`、`AnimSpeed = 1`、`Duration = 0.5s`
- 逻辑 `nt` 在 0.5s 时达 1 → `actionEnded=true` → `ExitToBaseline` → `Change<Locomotion>`
- 但动画播了 0.5/1.5 = 33% → 被强行打断 → **视觉上"闪一下回 Idle"**
- 用户感觉是"播完才动" —— 实际是"逻辑时钟到点了，但动画只播了 1/3，然后切回 Idle，位移由下一帧 MoveByLocomotion 接管"

反过来如果 `Duration = 2.0s` 而 `Clip = 0.5s`：动画播完后角色处于 Clip 末帧姿势 1.5s 静止 → 这就是 #1 的"播完动画才执行位移"。

**Bug 关键**：`ResolveAnimWallClockSeconds` 的 if 分支无效；AnimSpeed 不自动同步到 Duration；二者只能任凭设计师手算"`AnimSpeed = Clip.length / Duration`"——一旦没算对就出现"闪 / 播完才动"。

### Bug #3 —— WalkEnd/RunEnd 中断重播 Start（latch 同步问题）

#### 关键代码

**`PlayerLocomotionState.OnEnter`** —— 163.1 修复后：

```csharp

m_lastWantsRun = player.WantsRun;
```

**`PlayerActionState.TryConsumeGameplayIntent:220`** —— 打断仲裁：

```csharp
if (!ActionInterruptResolver.CanInterrupt(m_action, m_prevNormalizedTime, in intent, ...))
    return false;
// 通过 → NotifyRouteExited(interrupted) → IntentRouter.Route → Change<LocomotionState>
```

#### latch 时序竞态

| 时刻 | 状态 | m_lastHadInput | hasInput | 备注 |
|---|---|---|---|---|
| T0 跑动按 W | Loco | true | true | 持续 Move |
| T1 释放 W → release edge | Loco | false | false | RunEnd 触发 + Change<Action> |
| T2 ActionState 播 RunEnd | Action | (stale) | (动) | OnEnter 时 m_lastHadInput **被同步到 ActionState 入境瞬间的 hasInput=false** |
| T3 RunEnd 后摇期玩家按 W | Action | — | true (新输入) | Move intent 入队 |
| T4 ActionInterruptResolver.CanInterrupt OK → Change<Loco> | Loco | **player.HasMovementIntent=true → 同步为 true** ★ | true | OnEnter 把 latch 同步为当前 (true) |
| T5 Detect | Loco | true | true | **非 press 边沿 → 直接 Move Loop** |

**理论上 T5 应该走 Move Loop**，不应重播 Start。

⚠️ **但是**——如果用户经历的是 **"刹车动画中按一下 W 然后立即松开"** 的极端情况：
- T3 hasInput=true → 触发打断
- T4 进 Loco 同步 m_lastHadInput=true
- T4.5 在 Loco 的下一帧前，用户松开 W → InputReader 写 hasInput=false
- T5 Detect: m_lastHadInput=true, hasInput=false → release edge → **触发新 WalkEnd / RunEnd**！
- T6 用户再按 W → m_lastHadInput=false, hasInput=true → **press edge → WalkStart** ← **这就是 #3 现象**

或者更普遍地：每次"刹车被打断 + 后续输入变化"都可能误触发 Start↔End 切换循环。

#### 根因

**latch 同步只发生在 OnEnter（一次）**；进入 Loco 后的多帧内，latch 衰减完全依赖 Detect 的边沿对照，**没有任何短期"忽略边沿"机制**。

164.1 §13.4 提到的"奥德赛 Start↔Idle 切换"在站立连点时是**预期行为**；但 RunEnd 后摇期被打断后立刻 Start 是**非预期** —— 二者需要区分。

### 解法 #C —— WalkEnd 后摇期 latch 隔离（修 #3）

#### 思路

进入 Locomotion 后**前 N 帧内**抑制边沿检测（既不 press 也不 release），强行走 Move Loop 或 Idle。N 取决于"上一个 Action 是否是 End 类离散段"。

#### 字段 + 入口同步

```csharp
// PlayerLocomotionState 新字段
private int m_inputEdgeSuppressFrames = 0;
private const int EdgeSuppressFramesAfterEnd = 3;  // 3 帧 ≈ 50ms 缓冲

// OnEnter 加：刚结束 *End 类 Action 时设抑制帧
if (player.GetLastActionEndStateHint() == LocomotionStateId.WalkEnd
    || player.GetLastActionEndStateHint() == LocomotionStateId.RunEnd)
{
    m_inputEdgeSuppressFrames = EdgeSuppressFramesAfterEnd;
}

// DetectRequestedState 顶部
if (m_inputEdgeSuppressFrames > 0)
{
    m_inputEdgeSuppressFrames--;
    // 强行同步 latch，跳过边沿
    m_lastHadInput = hasInput;
    m_lastWantsRun = player.WantsRun;
    return hasInput ? LocomotionStateId.Move : LocomotionStateId.Idle;
}
```

`Player.GetLastActionEndStateHint()` 由 PlayerActionState.OnExit 写入 → Player 私有字段 → Loco.OnEnter 读取后清。

#### 效果

| 时刻 | m_inputEdgeSuppressFrames | Detect 结果 |
|---|---|---|
| T4 进 Loco（来自 WalkEnd 打断） | 3 | 强 Move |
| T5 | 2 | 强 Move |
| T6 | 1 | 强 Move |
| T7 | 0 → 恢复正常 | 正常 Detect |

3 帧内即便 hasInput 变化也不触发边沿 → 不再 Start↔End 误切换。

#### 不影响奥德赛行为

奥德赛 Start↔Idle 切换发生在**站立 → 按下 → 松开 → 按下** 链上。每次进入的 Action 是 WalkStart（不是 End）→ 抑制帧不触发 → 正常奥德赛行为保留。

## 十、追加 3 个新问题（v2 增量）

### Bug #5 —— 跳起后无法 WASD 前进 / 转向

#### 代码事实

**`PlayerAirborneState.OnLogicUpdate:181`**：
```csharp
player.MoveByLocomotionIntent(player.AirMoveMultiplier, player.WantsRun);
```

理论上 Airborne 内每帧调用此方法 → 应响应 WASD。

#### 时序复盘

```
帧 N   : Locomotion + Jump 意图 → Airborne.OnEnter
        · ConsumeJumpFromIntent=true → player.Jump() (vy=12)
        · TryArmJumpStartActionFromProfile → _pendingJumpStartArmed=true
帧 N+1 : Airborne.OnLogicUpdate
        · _pendingJumpStartArmed → ArmPendingAction(JumpStart) → Change<ActionState>
帧 N+1 : ActionState.OnEnter 播 JumpStart Action（Duration = ?）
帧 N+1 ~ N+K : ActionState 持续播放 JumpStart
        ★ 期间 WASD 不响应（Action 不调 MoveByLocomotionIntent；MotionExecutor 可能锁定位移）
帧 N+K : Action 结束 → ExitToBaseline
        · IntentCategory=Locomotion → 不进 JumpLand 分支 → Change<Locomotion>
帧 N+K+1 : Locomotion.OnLogicUpdate
        · !IsGrounded → Change<Airborne>
帧 N+K+2 : Airborne.OnLogicUpdate
        · MoveByLocomotionIntent ← ✓ WASD 终于响应
```

**根因 = JumpStart Action 占用整个跳跃上升段**：
- 若 JumpStart Action 的 Duration ≥ 跳跃上升时长（≈ 0.6s with JumpForce=12 / gravity=30）→ 整个跳跃过程都在 ActionState，WASD 永不响应
- 即便 Duration 短（0.15-0.25s），由于 Bug #1 的双时钟撕裂，nt 与 Clip 不同步可能让 Action 占用比预期长

#### 解法

**方案 A（推荐）**：JumpStart Action 期间允许 WASD 微调 —— PlayerActionState 在 IntentCategory=Locomotion 且 m_action.IsJumpStart=true 时主动调 `MoveByLocomotionIntent(player.AirMoveMultiplier, ...)` 叠加 MotionExecutor 位移。

或：

**方案 B（更简单）**：JumpStart Action **不切 ActionState**——把它做成 164.1 §13.1 的 IsContinuousLocomotion 模式，Airborne 状态内直接 CrossFade 到 JumpStart Clip + Animator 自动接 JumpLoop，Airborne.OnLogicUpdate 每帧调 MoveByLocomotionIntent → WASD 全程响应。

或：

**方案 C（最小改）**：限制 JumpStart Action Duration ≤ 0.20s + Action 期间 PlayerActionState 也调 MoveByLocomotionIntent（仅当 IntentCategory=Locomotion）。

#### 推荐：方案 C → 后续可升级方案 B

L5：`PlayerActionState.OnLogicUpdate` 在 Locomotion 车道 Action 下额外调 `MoveByLocomotionIntent(player.AirMoveMultiplier, player.WantsRun)`（仅 m_startedWhileAirborne || !IsGrounded 时）。

```csharp
// PlayerActionState.OnLogicUpdate 末尾、ExitToBaseline 检查前
if (m_action != null
    && m_action.IntentCategory == ActionIntentCategory.Locomotion
    && !player.IsGrounded)
{
    // Locomotion 车道的 Action 在空中允许 WASD 微调（与 MotionExecutor 叠加）
    player.MoveByLocomotionIntent(player.AirMoveMultiplier * 0.5f, player.WantsRun);
}
```

`* 0.5f` 是为了避免 MotionExecutor Z 曲线 + 玩家输入 双叠造成超速；视手感调整。

### Bug #6 —— Combat Graph 多 Stage 单 Route 卡僵

#### 用户陈述

> Graph 中我定义了一套 LM 触发的连招，最后一招从空中下劈。下劈结束后无法正常回到 Idle，僵持。
> **但用 3 个同样 Clip 但不同 Action 的多 Route**，则可以正常恢复。

#### 代码事实

**`PlayerActionState.cs:166-175`** —— Action 结束条件：
```csharp
var route = player.SkillEntries?.ActiveRoute;
var routeEnded = route == null || !route.IsActive;
var actionEnded = nt >= 0.9999f;
var stageCompleted = route?.Stage?.Completed ?? false;  // ★ 算了但没用！
if (actionEnded && routeEnded)
{
    ExitToBaseline(player);
}
```

⚠️ **`stageCompleted` 计算了却没参与判定**。等同于注释——只 `actionEnded && routeEnded`。

#### 双轨现象解释

| 配置 | route.IsActive 何时变 false | 退出条件 |
|---|---|---|
| **3 个独立 Route（用户能跑通的）** | 每个 Route 只有 1 个 Stage；播完 → 路由收尾 → IsActive=false | `actionEnded && !IsActive` 同时满足 → ExitToBaseline |
| **单 Route 多 Stage 连招（用户卡僵的）** | Stage 1/2/3 之间走 Transition；Route.IsActive 在**最后 Stage 完成 + 显式 Transition 离场**时才 false | 最后 Stage 完成但没 Transition 离场 → IsActive 永远 true → **僵在那里** |

**根因**：Combat Graph 内连招最后一段的 SkillStageDefinition 必须配置一条 "Transition to Exit"（或类似的尾端转移）。**资产侧**漏配 → 卡僵。

#### 解法（双管齐下）

**解法 #D1 — 资产层（用户操作）**：

打开最后一段 Stage（空中下劈对应的 `SkillStageDefinition`）：
- 给 `transitions[]` 加一条 **Auto Trigger** 转移：`OpenTime=1, CloseTime=1, TriggerKind=Auto, NextStage=null（或 Exit）`
- 配 `Condition.Always` → Stage 末段自动收尾，Route 退出

**解法 #D2 — 代码层（防御性兜底）**：

`PlayerActionState.OnLogicUpdate` 退出条件改为：

```csharp
// 165.1 #6 修复：多 Stage 单 Route 最后一段无显式 Transition 时的防御性兜底
//   原 actionEnded && routeEnded 要求 Route 主动收尾；缺一条 Auto Transition 就僵。
//   新增分支：actionEnded && stageCompleted && route.IsLastStage → ExitToBaseline
var route = player.SkillEntries?.ActiveRoute;
var routeEnded = route == null || !route.IsActive;
var actionEnded = nt >= 0.9999f;
var stageCompleted = route?.Stage?.Completed ?? false;
var isLastStage = route != null && route.IsLastStage;

if (actionEnded && (routeEnded || (stageCompleted && isLastStage)))
{
    ExitToBaseline(player);
}
```

需要在 `SkillRouteRuntime` / `IRouteRuntime` 暴露 `bool IsLastStage` 属性。

#### 推荐

资产侧 #D1 先修（用户立刻可做，0 代码改动）；同时落 #D2 作为防御兜底（避免未来漏配再卡僵）。

## 十四、设计理念强化 — Graph 是「合法上下文池」，不是「Clip 来源」

### 14.1 用户原话契约

> Graph 配置 Locomotion，只作为类似 Route Pool 和 Action Pool 一样的职责，**用于进行合法上下文编辑**，而不是状态的 Clip 获取来源。**状态与动画播放的关系应该由 LocomotionProfile 建立的映射关系决定**。

这一条契约直接修订 §二 §B（Land 单源化）的优先级链，钉死 **单一权威来源**。

### 14.2 三个数据源的最终角色钉死

| 数据源 | 真正职责 | **不该承担**的职责 |
|---|---|---|
| **`SkillEntryLoadoutSO.LocomotionGraphContext.{JumpStart, JumpLoop, JumpLand, …}`** | **Combat Flow Graph 编辑器内的合法上下文池** —— 让 Graph 编辑器能把 JumpLoop 标为 SourceOnly 节点，画 `JumpLoop → DownSlash` 派生边等 | ❌ **不**做运行时 Clip 获取来源；❌ **不**作为 Locomotion 状态机的播放映射 |
| **`LocomotionProfile.Bindings[<StateId>].Action`** | **唯一权威**的"状态 → 动画/动作"映射 —— Resolver / Locomotion 状态机据此查表播放 | ❌ **不**承担 Combat Graph 派生（那是 LocomotionGraphContext 的事） |
| **`PlayerAnimManagerSO.GetEntry("Airborne_Land")` 字符串 key** | 最终降级兜底 —— **仅当 Profile 未配 + Graph Context 也未配** 时的"什么都不挂"保险丝 | ❌ **不**作为新角色的主要播放来源 |

### 14.3 与 157.3 GraphParticipation 的呼应

回顾 157.3 引入的 C 轴：

```
GraphParticipation: None / SourceOnly / Full
```

- **Locomotion 类 Action**（JumpStart / JumpLoop / JumpLand / WalkStart / RunStart / WalkEnd / RunEnd / Stop / Pivot 等）→ 全部 `SourceOnly`
- 含义：**可出现在 Graph 编辑器作为派生源** + **Graph 求值器不对其进入做二次闸门** + **真正的播放权由 LocomotionProfile 决定**

`LocomotionGraphContext` 的存在就是为了让 Combat Graph 编辑器**看见**这些 SourceOnly 节点（在节点池里选得到、画派生边时找得到）。它本质是 **编辑期可见性 + 派生关系编辑** 的数据源，**不是运行时播放查询表**。

### 14.4 §二 §B 优先级链终态修订

```
旧（v1）：
  Profile.JumpLand  →  ctx.JumpLand（兼容期兜底）  →  AnimLibrary

新（v2 钉死单源）：
  Profile.JumpLand（唯一权威播放来源）
     │
     └─ 缺失 → AnimLibrary（"什么都没配"最终保险，给 Console 警告）

  ctx.JumpLand → **完全不参与运行时播放**
                  仅作 Combat Graph 编辑器内的合法上下文（节点可见性 + 派生边）
```

`PlayerAirborneState.TryExitToLandOrLocomotion` 改为：

```csharp
static void TryExitToLandOrLocomotion(Player player, float fallHeight)
{
    player.PublishEvent(new PlayerLandedEvent(...));

    // 唯一权威：LocomotionProfile（与 §B PickJumpLandFromProfile 一致）
    var landAction = PickJumpLandFromProfile(player, fallHeight);

    if (landAction != null)
    {
        // 仅作日志/调试用；不作为 Combat 路由意图
        player.SetGraphContextAction(landAction, "jump-land");
        player.ArmPendingAction(GameplayIntentKind.Jump, landAction);
        player.States.Change<PlayerActionState>();
        return;
    }

    // 没配 Profile.JumpLand → 告警 + 走 Locomotion；OnLanded 兜底播 AnimLibrary
    if (player.DebugLocomotion)
    {
        Debug.LogWarning(
            "[Jump][Land] LocomotionProfile.JumpLand 未配置；走 AnimLibrary.Airborne_Land 兜底。" +
            "请在 LocomotionProfile.Bindings 注册 JumpLand。",
            player);
    }
    player.ClearGraphContextAction("land-no-profile");
    player.States.Change<PlayerLocomotionState>();
}
```

> 注意：旧 `ctx.JumpLand` 的读取**整段移除**。即便 Combat Graph 编辑器内还有 JumpLand 节点（作派生源），运行时落地完全只走 Profile。

### 14.6 PlayerAirborneState.OnEnter 一致性修订

OnEnter 里的 `player.SetGraphContextAction(ctx.JumpStart, "jump-start")` 等调用 —— 这是写 **Combat Graph 运行时上下文**（让 Graph Runner 知道当前"派生源节点"是谁），**不是**播放指令。保留 ✓，但要确认：

- 同时 **不**用 ctx.JumpStart 决定播放 → ✓ 当前已经走 LocomotionProfile.JumpStart（158.2 L5 落地）
- JumpLand 路径同样 → §14.4 改完后只走 LocomotionProfile.JumpLand

### 14.7 编辑器侧契约（用户操作指引）

| 操作 | 配在哪 | 用途 |
|---|---|---|
| 设置"角色跳起播什么 Clip" | `LocomotionProfile_<Char>.Bindings[JumpStart].Action` | 唯一播放来源 |
| 设置"角色落地播什么 Clip" | `LocomotionProfile_<Char>.Bindings[JumpLand].Action` | 唯一播放来源 |
| 想画 `JumpLoop → DownSlash` 派生边 | `SkillEntryLoadoutSO.LocomotionGraphContext.JumpLoop` 引用一个 Action SO（与 Profile 里同一个或不同都行）→ Combat Graph 编辑器内即可看见此节点 → 拖边到 DownSlash | Graph 编辑期可见 |
| 临时调"AnimLibrary.Airborne_Land" 不挂 Profile | 仍可用，但 Console 出警告 | 兜底降级 |

**关键认知**：`LocomotionGraphContext` 与 `LocomotionProfile` 配的同一个 Action SO 可以**指同一份资产**，但二者的"读取目的"完全不同：
- LocomotionGraphContext.JumpLand → Combat Graph 编辑器看见 JumpLand 作派生源
- LocomotionProfile.Bindings[JumpLand].Action → 运行时落地真正播这个 Action

二者**不互相替代**，**职责互相正交**。

### 14.10 设计理念汇总（一句话）

> **三句话钉死**：
>   1. `LocomotionProfile.Bindings` = **唯一**的"状态 → 动画/动作"映射来源（运行时播放）
>   2. `SkillEntryLoadoutSO.LocomotionGraphContext` = **Combat Graph 编辑期**的合法上下文池（Action Pool / Route Pool 同等地位）
>   3. `PlayerAnimManagerSO` = **完全没配 Profile** 时的兜底保险，给警告

任何把 ②③ 当成运行时 Clip 来源的代码路径都属于**职责倒挂**，必须移除。
