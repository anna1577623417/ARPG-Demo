# 当前输入 → 技能框架分析与 SO 资产工具设计技术文档

> 基线：Ver 4.3.5 工作树 + Ver 4.3.6 蓝图（路由运行时网络）。 本文档不生成新文件，仅以分析报告形式回答四个核心问题：
> 
> 1. 现框架数据流与配置管线
> 2. 多阶段技能 / 后摇 / 蓄力（单 Clip vs 多 Clip）的配置可达性
> 3. 已实现功能与可优化清单
> 4. SO 资产生成工具的设计方案（围绕「入口语义」与「动作语义」两套数据的对接）

## 一、现框架数据流回顾（从配置到运行时的两条管线）

整套系统由**两条互不直接耦合的资产链**在运行时通过 `intent.Action` 一点交汇：

### 1.1 入口语义管线（"按键 → 技能"）

```
[资产]   SkillLoadoutSO.bindings[]   (槽位 → SkillDataSO)
            ↓
         SkillDataSO  (CastType, ChargeConfig, comboChain[], stages[], cdPolicy)
            ↓
         SkillStageSO (Action, Tasks[], Transition, HitShape, TargetFilter)
            ↓                                  ↓
       SkillRuntime / ChargeCastHandler       intent.Action = stage.action
```

这条链回答的问题是：**"玩家按了 Q，应该跑哪一段子技能？"** 它管 CD、消耗、Combo 索引、二段窗、Charge 状态机、Tap 回退等**与按键意图直接相关**的所有事。

### 1.2 动作语义管线（"播什么动画 + 怎么位移"）

```
[资产]   ActionDataSO    (MainClip, MainClipDuration, AnimSpeed, Windows[],
                          Category, InterruptStability, MotionProfile)
            ↓
         MotionProfileSO (Displacement/Lateral/Warp 曲线, BaseDistance, ReferenceSpeed,
                          AnimSpeedMode, GravityBehavior, ScaleType)
            ↓
       PlayerActionState
            ├─ MotionExecutor.Begin/Tick (位移 + finalClipSpeed)
            ├─ PlayerAnimController.PlayMain (Playables 3 通道 + Crossfade)
            └─ ActionWindow 派发 (HitFrame / VFX / Sound / 标签写入)
```

这条链回答的问题是：**"既然要播这一招，怎么动、怎么播、什么时候出伤？"** 它**对按键、Combo、Charge 一无所知**——一份 `ActionDataSO + MotionProfileSO` 可被任意 SkillStage 复用。

### 1.3 两条管线唯一的握手点

`SkillSystem.TryPrepareIntentForSkills` 内部：

```
intent.Action = stage.action;   // ★ 唯一握手
```

外加一个**蓄力替身**握手（`SkillChargeCommit.TryApplyChargeOverride` 可覆盖 `stage / actionOut`），以及 `baseAnimSpeed = action.AnimSpeed` 这一标量经 `MotionExecutor.Begin` 注入。除此之外，**Action / Motion 不通过任何方式读取 SkillData / Charge 状态**——这是当前架构最干净的一处设计，也是 Ver4.3.6 蓝图明确要求保留的不变量（契约 C2）。

## 二、多阶段技能 / 后摇 / 蓄力（单 / 多 Clip）配置可达性评估

### 2.1 多阶段技能 — **部分可达，机制割裂**

现框架对"多阶段"提供了**三种不等价的实现**，配置者需自行决定走哪一条，且互斥性极强（文档原文："勿在同一根技能上混合"）：

|实现|数据载体|推进方式|适用场景|缺陷|
|---|---|---|---|---|
|(A) **Sheet 内 stages[]**|`SkillDataSO.stages[]` (SkillStageSO 数组)|`SkillRuntime.CurrentStageIndex` + `SecondStageAvailable` 二段窗|同一 Sheet 内部的 Q1→Q2|仅支持二段；推进逻辑硬编码（`OpenSecondStageWindow`）；无显式 Transition 条件|
|(B) **comboChain[] 跨 Sheet**|`SkillDataSO.comboChain[] : SkillDataSO[]`|`runtime.ComboIndex` + `comboResetTime` 超时回 0|横向连段（普攻 1→2→3→4）|切的是整张 Sheet，CD/资源/Trait 各自独立，难以"共享一份蓄力"|
|(C) **ActionDataSO.Windows[]**|`ActionWindow` 时间切片 + `ActionWindowEvent`|归一化时间触发|同一 Clip 内部的 HitFrame / VFX / Sound|只是动画事件总线，没有"切到下一个 ActionData"能力|

**结论**：现框架**能配置多阶段技能**，但**只到 2 阶（A 路）或纯横向连段（B 路）**，且**无 RequireHit / TargetRule 等条件门**——Q1 命中英雄才开 Q2 之类的盲僧 Q 范式**当前无法配置**。这正是 Ver4.3.6 蓝图 Phase 5 的核心目标。

### 2.2 后摇（Recovery） — **当前不可独立配置，只能"耗 Duration"**

现框架**没有"后摇阶段"的一等公民概念**。所有"出招 + 后摇"被打包成**单个 ActionDataSO**：

- `ActionDataSO.MainClipDuration` 是整段（前摇 + 出招 + 后摇）的墙钟时长；
- `ActionDataSO.Windows[]` 中 `InterruptibleByCategories` 在动画归一化时间的**后半段**开放，是"可被打断的后摇"近似实现；
- `MotionProfile.DisplacementCurve` 在 `t ∈ [0.7, 1.0]` 区间通常衰减为水平段，是位移上的后摇近似。

**评估**：可以**视觉上**实现后摇，但配置者必须**人工对齐三套时间轴**：

1. Clip 内动画后摇段
2. ActionWindow 的可打断窗口
3. MotionProfile 位移衰减段

任何一处错位（最常见：Clip 改完动画忘了同步 Windows）都会出现"动作播完了但状态没退出"或"打断窗口提早开"。

**蓝图态**："后摇 = 自动衔接的下一阶段"是非常合理的抽象——只要 Phase 1 的 `SkillStageDefinition.Transitions[]` 落地，且其中一项 Transition 配置为 `OpenTime=1.0, CloseTime=1.0, RequireInput=false, Conditions=∅`，**就等价于一个"无条件自动衔接的后摇阶段"**。这是 Phase 5 之后**零额外成本**就能得到的能力。

### 2.3 蓄力技能（单 Clip 模式） — **可达，链路成熟**

现框架对"单 Clip 蓄力"的配置路径相当完整：

|配置项|位置|作用|
|---|---|---|
|`SkillDataSO.castType = Charge`|Sheet 顶部|装配 ChargeCastHandler|
|`ChargeConfig.tapThreshold`|Sheet `charge` 字段|< 此值视作轻点 → Tap Fallback|
|`ChargeConfig.chargeFullTime`|Sheet `charge` 字段|满蓄时间|
|`ChargeConfig.maxHoldTime`|Sheet `charge` 字段|极限时间 + `expiryStrategy` 处理|
|`ChargeConfig.holdAnimSpeedAtFull`|Sheet `charge` 字段|蓄满后 Animator 压速（0=暂停, 0.05≈抖循环）|
|`ChargeConfig.damageMultiplierByProgress`|Sheet `charge` 字段|连续伤害倍率曲线（X = progress01）|
|`SkillStageSO.action.MotionProfile`|Stage|Motion 与 Charge 解耦，正常配置|

**运行时调度**：

- `SkillCastHandlerFactory.Create` 按 `castType=Charge` 产出 `ChargeCastHandler`；
- `BootstrapCastHandshake` 自动 `OnInputPressed`；
- `PlayerActionState` 每帧 `handler.OnUpdate(ctx, dt)` → 推进 `HoldSeconds`；
- 玩家松手 → `PrimaryAttackPressTracker / Player.TryNotifySkillCastInputReleasedForSlot` → `handler.OnInputReleased`；
- `SkillCastGating.ShouldDispatchTasksAndWindows` 在 `ShouldTrigger==false` 时屏蔽 HitFrame，松手后开闸。

**单 Clip 模式的代价**：必须将"前摇 / Hold循环 / 释放"打包进**同一个 Clip**，靠 `holdAnimSpeedAtFull` 把动画压到极慢实现"循环错觉"——美术若希望"前摇→进入呼吸循环→释放出招"三段是独立 Clip，此模式无法满足。

### 2.4 蓄力技能（多 Clip 模式） — **半可达，需借 chargeLevels 强行实现**

现框架**没有原生的"Startup / HoldLoop / Release 三 Clip 蓄力"模型**。最接近的实现是：

```
SkillDataSO.castType = Charge
    + ChargeConfig (定义时间锚点)
    + chargeLevels[] : ChargeLevel[]
         ├─ Level0  { minHoldTime=0.0, action=Action_Startup,  stageOverride=Stage_Startup  }
         ├─ Level1  { minHoldTime=0.6, action=Action_HoldLoop, stageOverride=Stage_HoldLoop }
         └─ Level2  { minHoldTime=1.2, action=Action_Release, stageOverride=Stage_Release  }
```

由 `SkillChargeCommit.TryApplyChargeOverride` 根据 `hold` 命中最大 `minHoldTime ≤ hold` 的档位，覆盖 `stage / action / damageMultiplier`。

**这条路径能跑，但有三处硬伤**：

1. **Override 在松手瞬间一次性应用**，蓄力过程中**屏幕上仍是 Startup Clip 在慢放**——美术希望"按住到 0.6s 时切到 HoldLoop Clip 循环"无法实现。
2. **无法表达"Cancel / 超时"的独立 Clip**——`expiryStrategy=Cancel` 时美术想播一个"力竭垂手"Clip 没有挂载点。
3. **HUD 完全看不到分级**——`SkillRuntime.IsCharging` 只有布尔，进度需要 HUD 自己计算 `(Time.time - ChargeStartTime) / chargeFullTime`，且**无法预览将要触发哪一档**。

**蓝图态**（Phase 3）：`ChargeRouteDefinition` 显式持有 `Startup / HoldLoop / Release / Cancel : SkillStageDefinition`，每个 Stage 各自挂自己的 Clip，通过 `MotionPlaybackContext.LoopWindow / Pause` 实现"HoldLoop 循环 + 松手切 Release"，**彻底解决三个硬伤**。

## 四、SO 资产生成工具设计（核心议题）

### 4.1 设计原则 — 与"两套语义"切割同构

蓝图与现框架的最重要架构观察：**`SkillRoute + SkillStage` 与 `Action + Motion` 是两个互不知情的资产体系**——前者带按键/入口语义，后者只描述"动作怎么演"。SO 工具必须**严格尊重这条边界**，**不能为了"一键生成"把它们合并**——那等于把"按键意图"塞进了 Animation Clip 元数据。

**正确做法**：工具是一个**双向同步的脚手架**，每次生成时**强制要求两份资产对齐**，但**资产仍各自独立持有**。具体落到三个原则：

1. **配方驱动**（Recipe-Driven）：工具读一份「配方 SO」(`SkillAuthoringRecipeSO`)，**根据配方推导**应当生成哪些 Route / Stage / Action / Motion 资产，并完成命名与目录组织。
2. **幂等可重入**：同一份配方多次执行只更新差异字段，**不重建 GUID**——保证已被 Loadout 引用的资产不会断链。
3. **可逆**：每个生成产物都打上 `AuthoringSourceRecipeGuid` 隐藏字段，工具菜单提供"反向同步：从资产回写配方"——便于策划手改 Inspector 后回笼到配方文件做版本对比。

### 4.2 工具分层架构

工具内部由四层组成，对应蓝图的三个 Phase 输出：

#### Layer 1：`SkillAuthoringRecipeSO`（配方资产 — 工具的输入）

```
SkillAuthoringRecipeSO
├─ EntryDesc       (slot, displayName, iconRef)
├─ NormalRouteDesc (clipRef, duration, animSpeed, windows[], motionPreset)
├─ ComboRouteDesc  (chain: ClipRef[], resetTime)
├─ ChargeRouteDesc (mode: Single|Multi,
│                   single:   { clipRef, holdLoopRange:[t0,t1] }
│                   multi:    { startupClip, holdLoopClip, releaseClip, cancelClip }
│                   chargeCfg: ChargeConfig (复用现枚举))
├─ MultiStageDesc  (stages[]: { clipRef, duration, transitions[] })
├─ DamageDesc      (per-route: base, scale, critOverride)
└─ HudHints        (showOnHud[], keyLabel)
```

配方是**唯一的策划入口**：策划填写 Clip 引用、参数、Transition 条件，工具自动产出资产 + 自动归位目录 + 自动写引用。

#### Layer 2：`SkillRecipeCompiler`（核心编译器 — Editor 命令）

负责执行 4 步固定流水线：

1. **资产规划**：读配方，确定要生成的资产清单（路径 / 命名规则 / 已存在则更新）。
2. **动作语义层产出**：对每个 ClipRef 生成 / 复用 `ActionDataSO + MotionProfileSO`：
    - `ActionDataSO` 命名规则：`Action_<EntryId>_<RouteType>_<StageId>.asset`；
    - `MotionProfileSO` 命名规则：`Motion_<MotionPreset>.asset`（**强复用**，配方选 preset 名而非 inline 定义）；
    - 动画 Clip 元数据通过 `AnimationUtility.GetAnimationEvents` 自动转 `ActionWindow.Events`；
    - `MotionProfile.BurstDurationSeconds` 自动从 `AnimationClip.length / AnimSpeed` 写回。
3. **入口语义层产出**：生成 / 更新 `SkillEntryDefinition + SkillRouteDefinition + SkillStageDefinition`：
    - Stage 内 `Action` 字段引用第 2 步的 `ActionDataSO`；
    - Charge 多 Clip 模式自动生成 4 个 Stage（Startup/HoldLoop/Release/Cancel）并按蓝图 `MotionPlaybackContext` 默认值预填 `LoopWindow`。
4. **双向校验**：检测两端不一致（如 `ActionData.MainClipDuration ≠ Stage.transition.OpenTime` 的归一化值），生成 `SkillRecipeReport` 报告资产树（绿色=已同步、黄色=差异、红色=断链）。

#### Layer 3：`SkillAssetMigrationTool`（迁移工具 — 一次性）

蓝图 Phase 7 要求把所有旧 `SkillDataSO` 转为新资产，工具菜单：

- `Tools/SkillRoute/Migrate Legacy SkillData`：扫工程，每张 `SkillDataSO` 生成对应配方 + 调 `SkillRecipeCompiler`；
- `Tools/SkillRoute/Sync Loadout Bindings`：批量把 `SkillLoadoutSO.bindings[]` 转为 `entries[]`；
- `Tools/SkillRoute/Verify All Recipes`：CI 用，校验所有配方产出与硬盘资产一致（用于 PR 检查）。

#### Layer 4：`SkillAuthoringWindow`（EditorWindow — 可视化前端）

只在以上三层之上做 UI，**不持任何编译逻辑**：

- 左栏：配方列表（树形）；
- 中栏：当前配方编辑（Foldout：Normal / Combo / Charge / MultiStage / Damage / HUD）；
- 右栏：实时预览 — 显示该配方将产出的资产树 + `SkillRecipeReport`；
- 顶栏按钮：`Compile / Compile All / Migrate Legacy / Verify`；
- 联动 Inspector：选中右栏某资产时高亮跳转到 ProjectView。

### 4.3 关键技术决策

|决策点|选择|理由|
|---|---|---|
|配方与产出资产关系|**1 配方 → N 资产**，资产持有 RecipeGuid 反查|维持「按键语义 / 动作语义」物理分离，又能可逆回写|
|ActionData 是否由 Recipe 独占|**否**，ActionData 是共享资产|一份"剑横劈"Action 可被普攻 / 派生 / Charge Release 三个 Stage 同时引用；Recipe 只决定**命名 + 默认参数**，已存在则提示复用|
|MotionProfile 复用粒度|**预设库**（`Motion_Slash_S / Motion_Dash_M / Motion_Charge_HoldLoop` 等命名预设）|防止配方泛滥 inline MotionProfile；策划改预设全局生效|
|Clip 解析|`AnimationUtility.GetAnimationEvents` 自动转 ActionWindow.Events，**未识别事件名仅警告不报错**|给美术留通道：自己在 Clip 上加 `OnHitFrame` 事件，工具识别后直接转为 `HitFrameEvent`|
|Charge 单/多模式切换|配方一个 enum `mode: Single|Multi`，编译器**不允许混用**且差异在 Report 中红色提示|
|Multi-Stage Transition 条件|配方内嵌**枚举条件构造器**：`OnTime / OnHit / OnInput / OnTimer / Combined`|不允许策划在 Inspector 手填 ulong 标签——一律走条件构造器生成 `SkillTransitionCondition`|
|资产命名 / 目录|工具**强制**目录结构：`Assets/_Skills/<EntryId>/Routes/`、`Assets/_Skills/<EntryId>/Stages/`、`Assets/_Skills/<EntryId>/Actions/`|杜绝"资产散落"；CI 校验目录与配方一致|
|编辑器友好度|所有 SO 类型实现 `ISerializationCallbackReceiver` + 自定义 `PropertyDrawer`|配合蓝图 Phase 8 的 Foldout Inspector 改造|

### 4.4 工具与运行时的握手契约

工具产物**进入运行时**时**禁止运行时反向修改**任何字段（除 CD / 充能 / Combo 索引等纯运行时状态字段，它们都放在 Runtime 类，不在 SO 内）。这条契约由两个机制保障：

1. SO 字段**全部加 `[SerializeField]` + 私有**，通过只读属性暴露——避免运行时误写；
2. `SkillRecipeCompiler` 输出时给每个 SO 写 `_authoringFingerprint`（配方 hash），运行时 `OnEnable` 校验：fingerprint 不匹配则 `Debug.LogError` 但不阻止运行（用于发现"手动改 SO 后忘了回写配方"）。

### 4.5 与蓝图各 Phase 的对接节奏

| Phase  | 工具该提供什么                                                                     |

## 五、对当前框架的总结性判断

1. **现框架的"两条管线 + 一个握手点"是健康的架构**——这是为什么蓝图重构能"内部翻新"而不必伤筋动骨。
2. **真正的瓶颈不是技术实现，而是配置语义不完整**：多阶段不能上条件门、后摇没独立载体、Charge 多 Clip 模式被 `chargeLevels` 假实现——三者都属于"配置者表达不出来"，而不是"运行时跑不动"。
3. **`SkillRuntime` 内承担了过多职责**（CD + Combo + Stage + Charge），需按蓝图 Phase 1 拆为 `RouteRuntime + StageRuntime`。
4. **`PlayerActionState` 内残留的 ChargeMicroPhase 是历史债**，与 `ChargeCastHandler` 重复，必须在 Phase 3 拔除。
5. **HUD 与 Skill 解耦不够**：HUD 透过 `SkillSlotType` 直读 SkillData，导致一个槽只能渲一个 Widget——Phase 4 的 `IRouteRuntimeHandle` 是唯一解。
6. **SO 资产工具不是"锦上添花"**，而是 Phase 1 一开始就该启动的**Day-1 基础设施**——没有它，配方→资产的产出会出现命名混乱 / 目录散落 / 引用断链，让重构的 PR 难以 review。
7. **配方 vs 资产** 的分离是工具设计最关键的一招：**策划编辑配方，工具生成资产**，资产**仅供运行时消费**，从而把"输入语义"（按键 / Combo / Charge）与"动作语义"（Clip / Motion 曲线）的物理分离**贯彻到编辑器层**——这正是文档要求的"两部分运行"的工具化兑现。
