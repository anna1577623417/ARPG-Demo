## §7 End 节点软化（**设计方案**）

### §7.1 问题

```
现状：
  Combo_A1 ─┐
  Combo_A2 ─┼─→ [End]
  Combo_A3 ─┤
  Combo_B1 ─┘
  Skill_X ─→ [End]
  Skill_Y ─→ [End]
  Dodge_Roll ─→ [End]

→ End 是单一吸收节点；每条链尾都拉一条线连过去
→ 节点位置摆放：要么把 End 挪到中心导致连线蜘蛛网；要么放角落但所有终结连线穿越整图
→ 视觉上 6 条链 = 6 条出尾连线 → 编辑器看着像蜘蛛网
```

### §7.2 设计：**Terminal Flag + 软 End**

**核心思路**：终结不是一种"节点"，而是一种"节点上的标记"。

```csharp
// CombatFlowNodeAuthoring 新增字段
[Tooltip("186.1 — 此 Action/Route 完成后是否归 Idle（无需连 End 节点）；OnComplete 触发。")]
public bool TerminalOnComplete;

[Tooltip("186.1 — 终结归位策略：FallbackToEntry / GoIdle / KeepCurrent。")]
public CombatFlowTerminalPolicy TerminalPolicy;
```

```csharp
public enum CombatFlowTerminalPolicy : byte
{
    FallbackToEntry = 0,   // 默认：回 Entry，下一帧重新解析
    GoIdle = 1,            // 显式归 Idle（不解析 Entry）
    KeepCurrent = 2,       // 当前 Action 自然结束，由 Runner 默认行为接管
}
```

### §7.3 编辑器视觉

FlowAction 节点右下角小角标 ⊥（"to End"）：
```
┌──────────────────┐
│ DownwardSlashAction │
│   [Action: ...]    │
│                   ⊥│  ← 一眼可见此节点是终结点
└──────────────────┘
```

- 角标颜色：FallbackToEntry = 灰；GoIdle = 蓝；KeepCurrent = 绿
- Inspector 顶部添加 `Terminal On Complete` checkbox + Policy 下拉

### §7.4 旧 End 节点的兼容

- **保留** `CombatFlowNodeKind.End` 枚举值与现有 End 节点
- 显式 End 节点仍允许（向后兼容）
- 验证器在节点同时是 `TerminalOnComplete=true` 与"连出 End 边"时给 INFO："冗余：建议二选一"
- 资产迁移工具：扫描 `OnSegmentComplete → End` 这类 Edge，**自动**把 Source 节点标 `TerminalOnComplete=true` 并删除该 Edge（可选 dry-run 确认）

### §7.5 运行时行为

`CombatGraphRunner` 在 Action OnSegmentComplete 时：
```
1. 优先查找出边
2. 没有出边 OR 当前节点 TerminalOnComplete=true:
     → 按 TerminalPolicy 处理
       FallbackToEntry → 复用 GraphMissPolicy.FallbackToEntry 路径
       GoIdle → States.Change<PlayerLocomotionState>()
       KeepCurrent → 由当前 Action 自然结束接管
3. 有出边：照常评估 Conditions[]
```

→ **完全等价**于 "连一条到 End 节点 + Runner 在 End 时归 Idle"，但**无需画连线**。

### §7.6 视觉收益对照

| 场景 | 旧（必须画 End）| 新（Terminal Flag）|
|---|---|---|
| 单链 Combo（3 段）| 3 条线汇聚 End | 仅在最后一段勾 ⊥；零汇聚线 |
| 多技能并列（6 个）| 6 条线汇聚 End | 6 个 ⊥ 角标；零汇聚线 |
| 混合（部分终结、部分链转）| End 与中间节点混摆 | 链路与终结正交：链画线，终结勾标 |

## §9 关键约束（**避免走偏**）

1. **不在 Edge 上保留任何"旧"条件入口** —— 删字段、删 Pool、删 Drawer，砍干净
2. **SkillTransitionCondition struct 保留** —— 它是运行时编译产物的载体，与 Authoring 解耦
3. **时间窗仍归 Action**（185.2 已声明）—— 迁移工具遇到 TimeWindow 类 Legacy 条件直接跳过 + INFO
4. **End 节点保留但不强求** —— 向后兼容；新项目优先 TerminalOnComplete
5. **TerminalPolicy 三档不增加** —— 三档（FallbackToEntry / GoIdle / KeepCurrent）已覆盖所有现有 End 行为；勿加 Custom 等扩展点

## §10 三句话沉淀

> 1. **Edge 上只能有一套条件系统** —— EdgeConditionSO 是新唯一入口；Legacy 全删
> 2. **终结不是节点种类，是节点标签** —— TerminalOnComplete=true ⊥ 取代必连 End 节点
> 3. **Valid 消息要分点** —— 每条独立编号、E/W 分类、空行分隔，便于策划逐条修

## §12 SemanticConfigSO（Input → Semantic Config）—— **保留**

### §12.1 定位

```csharp
// 玩家级输入语义配置（4_Data/1.Skills/Input/SemanticConfigSO.cs）
public sealed class SemanticConfigSO : ScriptableObject
{
    // Per-slot：TapThreshold / ComboWindow / EnableDirectional
}
```

它配置的是 **InputSemanticResolver 的"前段处理器"参数**：
- `TapThreshold` —— 按住越过 N 秒派发 Charge intent
- `ComboWindow` —— 上一连段后 N 秒内允许 Combo 衔接
- `EnableDirectional` —— 是否启用方向 Modifier

### §12.2 与新系统的关系

| 维度 | SemanticConfigSO | EdgeCondition / AbilityGate |
|---|---|---|
| 职责层 | **输入前段**（按键 → 时态分解 Tap/Hold/Combo/Directional）| 输入后段（已分解的 intent → 选 Route / 流转）|
| 时机 | InputSemanticResolver 解析阶段 | EdgeConditionEvaluator / RouteResolver 阶段 |
| 决策对象 | 把 RawInput 分类成什么"语义" | 已知语义后能不能走某条路 |

**零重叠**。SemanticConfigSO 是"输入流水线第一站"，新系统都在它之后。

### §12.3 结论

✅ **保留**。它解决的是"按住多久算 Charge"等手感参数集中化问题（112.1 重构成果），与 Graph 流转系统完全正交。

## §14 EdgeCondition Input SO vs Edge.InputSlot/Semantic —— **重复，统一到 EdgeCondition**

### §14.1 重复事实

```csharp

// 旧（147.1）—— CombatFlowEdgeAuthoring 字段

public InputSemanticType InputSemantic;

// 新（185.2）—— InputConditionSO
```

策划在 Edge 上同时看到两组字段，无所适从。运行时也存在"快路径用 Edge 字段、慢路径用 Conditions"的并行评估。

### §14.2 历史背景

147.1 把 Slot/Semantic 做成 Edge 字段是为了"OnInput 边的快速过滤"（避免对每条 OnInput 边都创建 SO）。185.2 EdgeCondition 引入后，性能不再是问题（条件评估发生在时间窗 + 一级闸门通过之后，频率很低）。

### §14.3 收敛方案

**保留**：
- `Edge.Transition == OnInput` 枚举（仍需区分触发方式）
- `Edge.Transition == OnSegmentComplete / Immediate`（自动流转）

**删除**：
- `Edge.InputSlot` 字段
- `Edge.InputSemantic` 字段

**迁移**：
- Validator 警告 "OnInput 未配置 InputSlot/Semantic" 的语义改为："OnInput 边未配置 `InputConditionSO`"
- 一次性 EditorTool 扫所有 OnInput 边 → `(Slot, Semantic)` 二元组自动 `CreateAsset` 为 `EdgeCondition_Input_*.asset` 并填入 `EdgeConditions[]`
- 资产名规则：`EdgeCondition_Input_LM_Tap.asset` / `EdgeCondition_Input_Space_Directional.asset`（同名复用，避免炸资产）

### §14.4 结论

✅ **退役 Edge 字段，统一到 InputConditionSO**。运行时性能影响可忽略（OnInput 频率本就低）。

## §15 AbilityMap vs Route.abilityGateRules —— **AbilityMap 可退役**

### §15.1 现状两套准入

```csharp
// AbilityGateService.cs
public static bool CanActivateRoute(SkillRouteDefinition route, in ctx, out reason)
    => route.PassesAbilityGates(in ctx, out reason);
    // ← 走 Route.abilityGateRules[]（138.1）

public static bool CanActivateFlow(SkillEntryLoadoutSO loadout, slot, ability, in ctx)
{
    if (!loadout.AbilityMap.TryGetRule(slot, ability, out var rule)) return true;
    return rule.Pass(in ctx);
}
    // ← 走 Loadout.AbilityMap（136.1）
```

### §15.2 两套谁权威？

| 入口 | 走的路径 | 评估对象 |
|---|---|---|
| 起手（玩家按键唤起新 Route）| `CanActivateRoute` | 目标 Route 自己持有的 `abilityGateRules[]` |
| 流转（Graph 边触发跳转）| `CanActivateFlow` | Loadout 全局 `AbilityMap` 中 `(slot, ability)` → Rule |

**问题**：流转的目标节点也是 Action / Route。如果目标 Route 本身就有 `abilityGateRules`，那么 `CanActivateFlow` 这一层 Loadout Map 是**冗余的二次映射**。

### §15.3 用户洞察（已成立）

> 后者把闸门下放到 Route 层面，起始无需 Map 也能运行了

**正确**。Route 持有自己的准入规则后：
- 起手 → 直接调 Route.PassesAbilityGates
- 流转 → Edge 的目标节点（FlowAction / RouteSwitch）的 Route / Action 应该自检
- Loadout.AbilityMap 这层全局表只是"在 Loadout 配置时把 (slot, ability) → Rule 的反向索引"

### §15.4 替代方案

| 旧 | 新 |
|---|---|
| `CanActivateFlow(loadout, slot, ability, ctx)` | `CanActivateRoute(edge.targetRoute ?? currentRoute, ctx)` |
| `Loadout.AbilityMap.TryGetRule(slot, ability)` | Route 自己的 `abilityGateRules[]` |
| 相位限制额外可用 | `PhaseConditionSO` 写在 Edge 上（更精细到边）|

### §15.5 迁移路径

1. 扫所有 `AbilityMap_*.asset`，把每个 `(slot, ability) → Rule` 反向写入：
   - 对应 Slot/Ability 的所有 Route，把 Rule 追加到 `Route.abilityGateRules[]`（如不冲突）
   - 冲突时打 WARN 让策划手工裁决
2. `CombatGraphRunner` 内 `CanActivateFlow` 调用点改为 `CanActivateRoute(targetRoute)`
3. 删 `SkillEntryLoadoutSO.AbilityMap` 字段 + `AbilityMapSO.cs` + Editor
4. `AbilityGateService` 简化为单一 `CanActivateRoute` 入口；`CanActivateFlow` / `CanActivate` 全删

### §15.6 结论

✅ **AbilityMap 可退役**，准入闸门完全下沉到 Route 层。`AbilityGateRuleSO` **保留**（它是规则定义，仍被 Route.abilityGateRules 持有）。
