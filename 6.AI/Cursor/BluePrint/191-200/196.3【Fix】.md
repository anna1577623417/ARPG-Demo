## 现象 A：Slide_Loop 入场"对冲帧" → 视觉闪现

### 证据（关键模式）

每次 Slide_Loop 启动后约 10 帧（即 Slide_Start → Slide_Loop **切换瞬间**），**连续两帧**位移：

|触发批次|帧 1|帧 2|量级|方向|
|---|---|---|---|---|
|第 1 次|429: +5.855 / +1.309|430: -5.813 / -1.300|~6.0m|**完全反号**|
|第 2 次|487: +5.822 / +1.302|488: -5.778 / -1.292|~6.0m|**完全反号**|
|第 3 次|580: -5.943 / -0.579|581: +5.895 / +0.574|~6.0m|**完全反号**|
|第 4 次|1238: -5.983 / +0.290|1239: +5.918 / -0.287|~6.0m|**完全反号**|
|第 5 次|1317: +5.993 / -0.290|1318: -5.927 / +0.287|~6.0m|**完全反号**|
|第 6 次|1366: +5.993 / -0.290|1367: -5.929 / +0.287|~6.0m|**完全反号**|
|第 7 次|1450: -5.975 / +0.263|1451: +5.934 / -0.261|~6.0m|**完全反号**|

### 关键数学

- planar ≈ **5.999m / 0.025s ≈ 240 m/s ≈ 864 km/h** —— 远超 Slide 设计速度（稳态后是 ~15 m/s）
- 两帧的位移量级 **几乎完全相等**，方向完全相反 → 净位移 ≈ 0.05m
- 之后从第 ~5 帧起进入稳态 0.30~0.55m/帧（=12~22m/s，**这才是 Slide 真实速度**）

### 根因推断（置信度高）

> **MotionExecutor 在 Slide_Start → Slide_Loop 这次 Action 切换瞬间，`prevT` / `_lastPos` 没有跟着新 Action 重置**。
> 
> 结果：
> 
> - **第一帧（+6m）**：Slide_Start 末段在 OnExit 那一次性结算它**整条曲线**的剩余位移（prevT 留在 ~0、currT 跳到 1.0），输出 +Scale·Δcurve ≈ +6m
> - **第二帧（-6m）**：Slide_Loop OnEnter 时 prevT 仍然 = 1.0（从 Slide_Start 末态继承），currT 重置为 0.025，所以 `SampleLocalDelta(1.0, 0.025) = curve(0.025) - curve(1.0) ≈ -6m`

这两帧合起来 = **整条 Slide_Loop 曲线被压在一帧里跑了两个方向**。眼睛看到的就是"角色往前一闪 → 拉回 → 再正常 Slide"。

### 排除项（看上去像但其实不是）

- ❌ **不是 MotionProfile 的 ZScale 配错**：稳态帧 0.4m/帧 × 0.025s × 总 duration = 4.8m，这是合理 Slide 距离
- ❌ **不是 Curve 形状错**：稳态帧数值平滑递增/递减，是正常曲线采样
- ❌ **不是 Slide_Start 自身的位移大**：Start 期间没有任何 MOTION_BURST（说明 Start 自己每帧 < 0.30m）

### 配置先排除（**先动这两个再说**）

1. **Slide_Start ActionData** 的 `MotionProfile.AxisCurves.ZScale` → 期望 ≤ 2m（确认它的整段位移设计就是几十厘米）
2. **Slide_Loop ActionData** 的 `MotionProfile.AxisCurves.ZScale` 与 `ZCurve` 末端 Key 值 → 期望 ZScale × ZCurve.max ≈ 4~5m
3. 看两份 MotionProfile 是不是**同一个**资产（如果共用，Loop 的 currT 重置就和 Start 撞车了）

但即使配置都对，**这个对冲帧也不会消失**，因为它是 MotionExecutor 的状态延续 bug，不是数据 bug。**等做"落地修复"那一步再动逻辑代码**。

## 现象 B：Slide_Loop 期间角色 Δyaw=+180° / +90° 异常转向

### 证据

```
[1238] MOTION_BURST Slide_Loop  ← Slide 入场对冲帧 1
[1239] MOTION_BURST Slide_Loop  ← Slide 入场对冲帧 2
[1242] FACING action=Slide_Loop Δyaw=+180.0° src=Player.SetLogicForward@ActionState   ← 紧跟 50ms 后
[1242~1252] MOTION_BURST Slide_Loop（稳态）
[1257] ROUTE kind=Move routed=Y note=→Loco   ← 这才是玩家方向键被路由

[1366] MOTION_BURST 入场帧
[1367] MOTION_BURST 入场帧
[1370] FACING Δyaw=+90.0°   ← 又是入场后 ~75ms

[1450] MOTION_BURST 入场帧
[1451] MOTION_BURST 入场帧
[1452] FACING Δyaw=+90.0°   ← 又是入场后 ~25ms
```

### 关键特征

1. **角度整数化**（90° / 180°）→ 不是玩家连续转动摇杆，而是被对齐到 **MovementIntent 的世界方向**（WASD 只能产生几个离散角）
2. **总在 Slide_Loop 入场后 25~200ms** 内触发 → 不是玩家反应时间内手动反向，是**逻辑层自动应用**
3. **晚于 MOTION_BURST 2~5 帧** → 不是 Action 启动那一刻的 burst face，是**第 3~5 帧某个机制把 LogicForward 重定向到了 MovementIntent**
4. `src=Player.SetLogicForward@ActionState` → 是 LogicForward 被直接 Set，不是 visualRoot 偷转

### 根因推断（置信度中-高）

候选 1（**最可能**）：**Slide_Loop 的 MotionProfile 没配置 V2 `FacingInputWeight` 曲线（或值 = 1.0）**，导致 Locomotion 系统在 Action 期间仍把"玩家输入对应的世界方向"喂给 SetLogicForward。

候选 2：**PlayerActionState 的 `m_burstFaceDir = ResolveMotionFacingDirection(...)`** 在某些条件下被写回 LogicForward（PlayerActionState.cs:79 处的解析），通常 burst face 是用于 Motion 方向的"一次性"取值，**不该写回 LogicForward**，需要核对它是否走了"写回"路径。

### 配置先排除

1. 打开 **Slide_Loop_ActionData → MotionProfile** 的 Inspector
2. 找新加的 **▸ V2 · Control / 玩家输入权重** Foldout：
    - **Facing Input Weight** 曲线 → 期望全段 = **0**（锁朝向）
    - **Move Input Weight** 曲线 → 期望全段 = **0**（不允许输入叠加位移）
3. 同时检查 Slide_Start / Slide_Exit 三份 Profile 是否一致

如果 Inspector 里看到的是空曲线 / Default 直线 1.0，那 V2 没在生效 → 这条**就是配置层的原因**。 如果 Curve 全 0 但日志依然出现 FACING，那说明 V2 通道存在但没被 MotionExecutor 消费 / 没被 PlayerActionState 尊重 → 是代码层。

## 现象 C：Walk_End 期间 D + Space 翻滚被吞

### 证据（对比表）

|帧 1070 Locomotion 期间 仅 Space|**Tap**|✅ Skill_Entry_08|翻滚成功|

### 关键差异

- 4 次失败：**sem = Directional**
- 1 次成功：**sem = Tap**
- 前 4 次都在 Walk_End Action 期间（InterruptibleByCategories 包含 Movement, Offense, Defensive, Utility, Locomotion 全 5 类 —— **理论上可以被打断**）
- Slide（Skill_Entry_07）在 Walk_End 期间用 **sem=Tap** 是可以成功打断的（例如帧 570、1355、1440）→ Walk_End 不是绝对锁死

### 关键发现：**没有 DROP 日志**

我的 probe 里 `LogIntentDropped` 只装在 `IntentRouter.Route` 内。**没出现 DROP** = Intent **根本没进 IntentRouter**。意味着它在更前面就被吞了：

```
SEMANTIC 出现 → 进 Player.EnqueueGameplayIntent → SkillEntryArbiter 仲裁 → IntentRouter.Route
                                                       ↑
                                              ← 就是被这一层吞了
```

### 根因推断（置信度中-高）

候选 1（**最可能**）：**Skill_Entry_08（Dodge/Roll）的 SkillRoute / Loadout 配置只对 `sem=Tap` 注册了 entry，没对 `sem=Directional` 注册**。所以 SkillEntryArbiter 收到 sem=Directional 后**找不到匹配 entry → 静默丢弃**，不进路由。

候选 2：**AbilityGateRule_Mobility_Grounded** 或类似 Recovery Gate 拒绝了 sem=Directional 的请求（你之前的 196.1 题里 RecoveryFlagFixer 已经处理过 IsLocomotionRecovery + InterruptibleByCategories，但可能还有一条 Gate 没覆盖 Directional 语义）。

### 配置先排除

1. 打开 **Loadout_Skill_C1.asset**，找 Space slot（Skill_Entry_08）
    - 看 `EnableDirectional` 是否 = true
    - 看绑定的 SkillRoute 是不是同一个支持 Tap 和 Directional 两种语义
2. 打开 **Route_Normal_Roll_Space**（或类似名字的 Skill_Entry_08 路由资产）
    - 看是否同时存在 `Tap` 入口节点和 `Directional` 入口节点
    - 如果只有 Tap 入口 → 这就是根因
3. 打开 **AbilityGateRule_Mobility_Grounded.asset**
    - 看它的过滤条件是否包含 `sem == Tap` 这种语义白名单
