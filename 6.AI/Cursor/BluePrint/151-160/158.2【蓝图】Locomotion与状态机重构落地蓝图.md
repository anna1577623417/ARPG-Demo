158.1 是用户层语义诊断；KB 是代码事实快照。两者交叉对照后，把"真实存在的债"和"误判"分离开。

## 二、根因诊断（一句话总结）

> **不是"Locomotion 绕过 Action 系统"，而是"Locomotion 没有把可离散化的过渡（Stop / Pivot / RunStart / JumpStart / TurnInPlace）抽成 Action 资产"。**

因此本蓝图的目标**不是重写状态机**，而是：

1. 把已有的"可离散过渡"挪进 Action 资产层（滑步 / 抽搐 / JumpStart 不播 自动消失）；
2. 把移动参数从 `PlayerStatsSO` 抽出，独立成 `LocomotionTuning` 资产（速度/系数/Buff 自动生效）；
3. 把 `PlayerAnimManagerSO` 升级为 `LocomotionProfile`（状态能力 + 动画集 + 降级），与 `ActionLoadout` 平级；
4. 引入**逻辑状态可选注册**（StopState 不注册即整段路径短路到 Idle，不依赖 Clip null 判断）；
5. 引入显式 `ControlOwner`（可观测，不改路径）。

## 五、三个正交资产（数据层）

### 5.1 `LocomotionStateRegistry`（逻辑层注册）

```csharp
[Flags]
public enum LocomotionStateFlag : ulong
{
    None       = 0UL,
    Idle       = 1UL << 0,   // 必有（基础）
    Move       = 1UL << 1,   // 必有（基础）
    Air        = 1UL << 2,   // 必有（基础）
    Dead       = 1UL << 3,   // 必有（基础）

    // 可选注册（不注册 = 逻辑降级到 Fallback）
    Stop       = 1UL << 4,   // 急停
    Pivot      = 1UL << 5,   // 原地转身（90/180）
    RunStart   = 1UL << 6,   // 起步加速
    JumpStart  = 1UL << 7,   // 起跳过渡
    JumpLand   = 1UL << 8,   // 落地恢复
    TurnInPlace= 1UL << 9,   // 锁定下的左右脚
    StrafeLeft = 1UL << 10,
    StrafeRight= 1UL << 11,
    BackWalk   = 1UL << 12,  // 锁定后退
    Sprint     = 1UL << 13,
}
```

注册=该角色拥有此状态能力；未注册=逻辑 Resolver 直接走 Fallback。

## 六、运行时层（最小改动）

### 6.1 `LocomotionResolver`（新；纯函数）

```csharp
public static class LocomotionResolver
{
    public static LocomotionDecision Resolve(
        in LocomotionIntent intent,
        in LocomotionContext ctx,
        LocomotionProfile profile)
    {
        // 一级降级：逻辑层
        var state = intent.RequestedState;
        while ((profile.EnabledStates & state.AsFlag()) == 0 && state != LocomotionStateFlag.Idle)
        {
            state = profile.GetBinding(state).FallbackState;  // 沿 Fallback 链回退
        }

        // 取绑定（Action 或 Clip）
        var binding = profile.GetBinding(state);

        // 二级降级：表现层（由 Animation 层在播放时做，本 Resolver 只产出决策）
        return new LocomotionDecision
        {
            ResolvedState = state,
            DiscreteAction = binding.DiscreteAction,  // 可为 null
            ContinuousClip = binding.ContinuousClip,  // 可为 null
            ControlOwnerHint = binding.CanMoveDuring ? ControlOwner.Locomotion : ControlOwner.Action,
        };
    }
}
```

### 6.2 `ControlOwner`（新；可观测枚举）

```csharp
public enum ControlOwner : byte
{
    Locomotion = 0,
    Action     = 1,
    Cutscene   = 2,
}
```

由 `PlayerStateManager` 在 `OnPreLogicUpdate` 末尾根据当前支柱写入 `Player.CurrentControlOwner`；**不参与裁决**，仅供调试 HUD / 日志展示。

> **为什么不让 ControlOwner 参与裁决？** KB-09§位移控制权矩阵显示当前互斥已通过支柱切换强制成立；引入显式 ControlOwner 参与裁决会产生**双轨真相**——状态切换说一套，ControlOwner 说一套，违反 09-refactor-delivery-protocol 的"单点真相"。

### 6.3 `PlayerLocomotionState` 改造（最小）

当前 `OnLogicUpdate`（已读过）：直接 `MoveByLocomotionIntent(1f, WantsRun)`。

改造为：

```csharp
// 1. 取意图 + 当前 Profile
var intent = BuildLocomotionIntent(player);
var decision = LocomotionResolver.Resolve(in intent, in ctx, player.LocomotionProfile);

// 2. 若 Resolver 决定走 Discrete Action（Stop / Pivot / RunStart）
if (decision.DiscreteAction != null)
{
    player.ArmPendingAction(GameplayIntentKind.Move, decision.DiscreteAction);
    player.States.Change<PlayerActionState>();
    return;
}

// 3. 否则连续 Clip 路径（沿用现有 MoveByLocomotionIntent）
ApplyLocomotionTuning(player, decision);   // 速度公式用 Tuning
player.MoveByLocomotionIntent(...);
player.ApplyMotor(MotorSolveContext.Locomotion);
```

**关键约束**：步骤 2 触发的 `Change<PlayerActionState>` 走标准 IntentRouter 路径——这里只是把"内部硬编码切 Pivot 动画"换成"提 ArmPendingAction"。

## 七、Landing 分解（5 落位）

> 前置：157.2 的 L1–L4 已落地（WASD 意图 + 落地窗口数据化 + 车道字段 + GraphParticipation + JumpLoop→DownSlash 验收）。158.2 在此之上。

### Landing 1/5 — 数据层落位（无运行时改动）

- **设施**：`LocomotionStateFlag` 枚举、`LocomotionProfile` SO、`LocomotionStateBinding` struct、`LocomotionTuningSO` SO、`LocomotionFeatureFlags` 枚举。
- **WIRE**：
  1. 三个新类型就位，可被 Inspector 编辑。
  2. 在角色 prefab 加 `LocomotionProfile` 引用字段（沿用 `Player.statsBlueprint` 模式）。

- **验收**：Inspector 能编辑 Profile；游戏运行**完全不受影响**（资产存在但未通电）。

### Landing 2/5 — ControlOwner 可观测 + Resolver 接线（行为不变）

- **设施**：`ControlOwner` 枚举、`Player.CurrentControlOwner`、`LocomotionResolver.Resolve`、`LocomotionContext` struct。
- **WIRE**：
  1. `PlayerStateManager.OnPreLogicUpdate` 末尾根据当前支柱写 `CurrentControlOwner`（Locomotion/Action/Cutscene）。
  2. CombatDebugHUD（已存在）+ 一行：显示 `Owner=Action/Locomotion`。
  3. `LocomotionResolver.Resolve` 实现，但 `PlayerLocomotionState` **暂不调用**——只在 `OnLogicUpdate` 顶部空跑一次，日志比对 `decision.ResolvedState == Idle/Move`，**不影响实际行为**。
- **验收**：
  - Console 日志能看到 `[LocoOwner] Owner=Locomotion/Action` 实时切换。
  - `[LocoResolver][DryRun] requested=Move resolved=Move discrete=null clip=Run_Loop` —— Resolver 决策与现状一致。
  - Play Mode 行为无回归。

### Landing 3/5 — LocomotionTuning 取代散落速度参数

## 十三、开放决策点（请确认后施工 L1）

1. **`LocomotionStateFlag` 是 Flags（多状态共存）还是 Enum（单值）？**
   - 建议 Flags：方便注册（一个 ulong 字段 = 全部能力）；运行时 Resolver 用单值。
2. **`LocomotionTuningSO` 与现有 `MotorSettingsSO` 是否合并？**
   - 建议**分开**：MotorSettings 是 KCC 物理参数（CapsuleSweep 步长等），Tuning 是 Gameplay 参数（速度倍率等）。混在一起策划改 Tuning 容易动到物理。
3. **`ControlOwner` 是 byte 枚举还是 ulong Flags？**
   - 建议 byte 单值（互斥语义，不需要并发持有）。
4. **二级降级（无 Clip/Action）由 Anim 层做还是 Resolver 做？**
   - 建议 Anim 层做：Resolver 只产出"应播什么"，Anim 层根据资产是否存在做最终降级，**关注点分离**。
5. **`PlayerStatsSO.presetWalk/RunSpeed` 在 L3 是 `[Obsolete]` 还是直接删？**
   - 建议 `[Obsolete]`：现有 `.asset` 文件序列化字段还在，强删会丢资产数据。下一个 Slice 再批量 `OnValidate` 迁移到 Tuning。
6. **L4 的 Stop/Pivot Action 是否复用 SkillEntry 系统？**
   - 建议**不复用**：Locomotion Action 走 `IntentRouter.Route(Move)` → `PlayerActionState`，不经过 `SkillEntryService`（157.2 已设计 A 轴 `Locomotion` 跳过 SkillEntry）。
7. **是否在 L2 阶段就把 ControlOwner 写到 Profiler 自定义事件？**
   - 建议是：Profiler 标记 Action vs Locomotion 区间，调优手感极有用。
