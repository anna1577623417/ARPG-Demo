## 〇、核心诉求蒸馏（来自 157.1 + 157.3）

| # | 诉求 | 关键句 | 来源 |
|---|---|---|---|
| 1 | **移动不进 Graph 二次闸门** | `Move/Run/Walk` 不是流转关系，是持续状态 | 157.1 |

| 6 | **落地特例归并** | 「落地动作可被移动打断」改为后摇窗口打断属性，纳入系统统一编辑 | 157.1 |

> **157.3 关键洞察**：「不在 Graph 中存在」≠「不进 Graph 二次闸门」。前者破坏可视化与派生表达（JumpLoop→DownSlash 无法表达），后者才是真正的诉求。等价命题：**Graph 描述 Action 之间的关系，而非审核所有 Action**。

## 一、现状代码事实（grounding，已核对）

```
Input ─┬─ Skill_Entry_NN ─┐
       └─ Jump ────────────┤
                           ▼
            IntentBuffer（仅缓冲 Jump + Skill_Entry_NN）
                           ▼
   PlayerStateManager.OnPreLogicUpdate
     1) TransitionResolver.CanOfferIntent（标签闸门）
     2) SkillEntries.TryResolveForIntent（Combat 才解析 Route）
     3) Current.TryConsumeGameplayIntent（支柱本地闸门 + 打断）
     4) SkillEntries.NotifyRouteEntered（提交 Combat Route）
                           ▼
   4 支柱：Locomotion / Airborne / Action / Dead
```

事实清单：

1. **`GameplayIntentKind`**：只有 `Jump` + `Skill_Entry_01..17`。**没有 Move/Walk/Run 意图**。
2. **WASD 是连续量**：`Player.MovementIntent` 被 Locomotion/Airborne 状态**直接读取**，从不入 `IntentBuffer`，因此**当前 WASD 无法参与仲裁、无法打断 Action 后摇**。
3. **打断仲裁单点**：`ActionInterruptResolver.CanInterrupt(action, nt, intent, incomingAction)` —— 看 `ActionWindow.InterruptibleByCategories`（位掩码）+ 优先级 + 自打断。
4. **打断语义类别**：`enum ActionCategory : ushort { None, Movement, Offense, Defensive, Utility }`（Flags）。Jump/Shift/Space 当前被 `ResolveIncomingCategory` 映射为 `Movement`。
5. **支柱本地闸门**：
   - `PlayerLocomotionState` / `PlayerAirborneState`：用注入的 `m_allowedCategories`（无时间轴，纯类别闸门）。
   - `PlayerActionState`：用 `ActionInterruptResolver`（窗口 + 类别）；Combat 还要过 **DUAL_GATE**（`LastIntentResolvedViaGraph` = Graph 边命中）。
6. **Graph 只参与 Combat**：`SkillEntries.GraphEnabled && ActiveRoute != null` 时才走双闸门；Jump 路径完全不碰 Graph（`IntentRouter` 直接切 Airborne）。
7. **「落地动作被移动打断」**：当前**不存在**数据驱动表达——落地相关 Action（Dive/Slide_Exit/JumpLand）后摇窗口并未配置 `InterruptibleByCategories=Movement`，且 WASD 根本没有意图通道。157.1 所说「局部操作」即此处缺乏统一表达。
8. **Locomotion Action 与 Graph 关系**：目前 `JumpStart / JumpLoop / JumpLand` 不作为 Graph 节点存在；空中接战（如 JumpLoop→DownSlash）**无法在 Graph 编辑器表达**，必须靠状态机硬编码或额外特例。157.3 所反对的即此处。

> 结论：诉求 1/3/4 **架构上已基本成立**（Graph 本就只服务 Combat）；真正缺的是 **②⑤⑥⑦⑧**——WASD 没有意图通道、落地特例没有数据化、Locomotion Action 无法以"上下文来源节点"身份进入 Graph 派生体系。

## 二、关键澄清：三个正交概念（不要混成一个）

157.1 + 157.3 同时引入了「ActionSlot / ActionCategory / GraphParticipation」等容易撞名的词，落地前先钉死**三个正交轴**：

| 轴 | 回答的问题 | 取值 | 现状 | 来源 |
|---|---|---|---|---|
| **A. 仲裁车道 `ActionIntentCategory`** | 这条意图走 **Combat 路由（SkillEntry→Route→Graph）** 还是 **全局仲裁**？ | `Locomotion / Combat / Reaction / Interaction` | **新增**（L3） | 157.1 |
| **B. 打断语义 `ActionCategory`（沿用）** | 「谁能打断我」——来袭动作算哪一类？ | `Movement / Offense / Defensive / Utility (+ Locomotion 新位)` | **已存在**，加位 | 157.1 |
| **C. Graph 参与度 `GraphParticipation`** | 我在 Graph 中以什么身份存在？ | `None / SourceOnly / Full` | **新增**（L4） | **157.3** |

- **A 决定路由**：`Combat → SkillEntry→Route→Graph→Action`；`Locomotion/Reaction/Interaction → 全局仲裁 → 对应支柱`，**不进入 Graph Resolve**。
- **B 决定打断许可**：`ActionWindow.InterruptibleByCategories` 是 B 的位掩码；任何来袭意图先映射成一个 B 类别再比对窗口。
- **C 决定 Graph 中身份**：
  - `None` — 不出现在 Graph 编辑器；纯内部/过渡动作。
  - `SourceOnly` — 出现在 Graph 编辑器，可作为**派生来源节点**与边的左端点，但 Graph 不对其本身进入做二次闸门。**Locomotion 类默认值。**
  - `Full` — 出现在 Graph 编辑器，参与 `Flow / Interrupt / Combo` 全部双闸门审批。**Combat 类默认值。**

### 三轴默认派生（A → C）

```
IntentCategory = Combat       → GraphParticipation = Full       (默认)
IntentCategory = Locomotion   → GraphParticipation = SourceOnly (默认)
IntentCategory = Reaction     → GraphParticipation = None       (默认)
IntentCategory = Interaction  → GraphParticipation = None       (默认)
```

ActionDataSO 仍以 **显式字段** 持有 `GraphParticipation`，允许策划覆盖默认（如某个 Locomotion 动作升格为 Full 闸门）。`OnValidate` 在"未显式设置"时按上表填默认。

### 为什么 C 轴必须独立于 A 轴（157.3 论证复刻）

如果只用 LocomotionTag/IntentCategory 绕 Graph，**JumpLoop 到底算 Locomotion 还是 Combat Context 会越来越模糊**（AirDash？WallRun？LockOnStrafe？这些都不是纯战斗但又与战斗关系巨大）。
所以：**A 轴回答"走哪个仲裁路径"，C 轴回答"在 Graph 中扮演什么角色"**。一个 Locomotion 动作完全可以同时是 Graph 中的 SourceOnly 节点 —— 这正是 JumpLoop→DownSlash 派生关系的表达基础。

### 单轨决策

- **B 加 `Locomotion = 1<<4` 位**，让窗口能表达「WASD 可打断我」；`Movement` 位继续表示翻滚/突进等**战斗位移**。WASD 走/跑映射到 `Locomotion`，Jump 按 157.1 语义也归 `Locomotion`。
- **C 新增 `GraphParticipation` 枚举**，**不动现有 `SkillTransition` / Graph 求值器结构**；Graph 求值器在求值边时检查 **目标节点** 的 `GraphParticipation`：若 `!= Full`，跳过双闸门直接放行（即"SourceOnly 节点可作为派生来源但自身免审"）。
- **不另起炉灶把 B 也改成 Locomotion/Combat**（会触发全资产 Category 大迁移、双轨期）。

## 三、终态架构（单轨）

```
                       ┌────────────── ActionIntentCategory（A 轴：车道）
                       │
Input ──▶ InputSemantic ──▶ GameplayIntent（统一缓冲，含 Move/Look/...）
                       │
        ┌──────────────┴───────────────┐
        ▼ Combat                        ▼ Locomotion / Reaction / Interaction
  SkillEntry→Route→Graph→Action    全局 Action 仲裁（不进 Graph Resolve）
        │                               │
        │   ┌── Graph 求值边 ──────┐    │
        │   │ edge.Target.C ?       │    │
        │   │   == Full  → 双闸门   │    │
        │   │   == SourceOnly →     │    │
        │   │     免审（仅作来源）   │    │
        │   └───────────────────────┘    │
        └──────────────┬───────────────┘
                       ▼
         ActionInterruptResolver（唯一打断单点）
            └─ 看当前 Action 窗口 InterruptibleByCategories（B 轴掩码）
                       ▼
              4 支柱（Locomotion / Airborne / Action / Dead）
```

### 典型链路：JumpStart → JumpLoop → DownSlash → JumpLand → Run（157.3 验收链）

```
[Locomotion 路径]
 Idle(SourceOnly) ── WASD ──▶ Run(SourceOnly) ── Jump 意图 ──▶ JumpStart(SourceOnly)
                                                                       ▼
                                                              JumpLoop(SourceOnly)
                                                                       │
                                          ┌── Attack 意图 ──────────────┘
                                          ▼
                              Graph 编辑器中边：
                              JumpLoop ──▶ DownSlash(Full)
                                          │
                              Graph 求值：来源 JumpLoop.C=SourceOnly 不审本节点进入；
                                        目标 DownSlash.C=Full → 双闸门通过 ──▶ 进入 DownSlash

 DownSlash 播完 ──▶ 着陆 ──▶ JumpLand(SourceOnly)
                                       │
                            后摇窗口 InterruptibleByCategories |= Locomotion
                                       │
                                WASD 边沿意图 ──▶ Run(SourceOnly)   ★ 落地无缝回归 Locomotion
                                       │
                            （从未为 Run/JumpLoop 配置 Graph 进入边）
```

### 要点

1. **WASD 升格为意图**：新增 `GameplayIntentKind.Move`，由 InputReader 在「Action 期 + 移动边沿 + 窗口放行 Locomotion」时入队；纯地面 Locomotion 维持现有直读路径不变（零回归）。
2. **A 轴决定是否进 Graph 路由**：`ActionIntentCategory.Combat` 才进 SkillEntry/Graph；`Locomotion` 直接进全局仲裁 → `ActionInterruptResolver` → 切 Locomotion 支柱。
3. **C 轴决定是否过双闸门**：边的**目标节点** `GraphParticipation == Full` 才过 Graph 双闸门；`== SourceOnly` 跳过双闸门（用于 SourceOnly 节点本身的"穿过"）。来源节点的 C 值**不参与求值**——它只决定该节点能否作为左端点出现在 Graph 编辑器。
4. **打断永远走同一单点**：无论 WASD 还是 Attack，都过 `ActionInterruptResolver.CanInterrupt`；区别只在「来袭类别（B）」与「目标节点是否还要过 Graph 双闸门（C）」。
5. **特例归并**：落地 Action 后摇窗口配 `InterruptibleByCategories |= Locomotion`，即「落地可被移动打断」，删除任何局部硬编码。

## 七、Landing 分解（每落位 ≤3 个 WIRE，单握手面）

### Landing 1/4 — WASD 升格为意图（最早可验证：进 Play Mode 跑/走打断后摇）
- **设施**：`GameplayIntentKind.Move`、`GameplayIntent.ForMove`、`ActionCategory.Locomotion` 位。
- **WIRE**：
  1. InputReader：Action 状态期间检测到移动边沿 → `IntentBuffer.Enqueue(ForMove)`（地面 Locomotion 期间**不**入队，零回归）。
  2. `ResolveIncomingCategory`：`Move → Locomotion`、`Jump → Locomotion`。
  3. `IntentRouter`：`Move → Change<PlayerLocomotionState>`（不碰 SkillEntry）。
- **本落位不做**：车道字段、落地资产、Graph 改动、GraphParticipation。
- **断点预期**：若某 Action 窗口未放行 Locomotion，`[Interrupt] allow=false cat=Locomotion reason=window-miss`（正确，说明通路通了只是数据没配）。

### Landing 2/4 — 落地特例归并为数据（删硬编码）
- **WIRE**：
  1. 定位并**删除**「落地可被移动打断」的局部硬编码（若存在）；统一走 `CanInterrupt`。
  2. 落地 Action 资产后摇窗口配 `InterruptibleByCategories |= Locomotion`（可用 ActionData 时间轴编辑器，无需新菜单）。
- **验收**：落地后摇期 WASD → `allow=true cat=Locomotion`；落地前摇期 WASD → `allow=false`（窗口未放行）。
- **本落位不做**：车道枚举重命名、全量资产批改、GraphParticipation。

### Landing 3/4 — 车道显式化（ActionIntentCategory）
- **WIRE**：
  1. `ActionDataSO.IntentCategory` 字段（默认 Combat）。
  2. `SkillEntryService`/仲裁前置：`IntentCategory != Combat` 的意图**跳过 SkillEntry/Graph 路由**，只过 `ActionInterruptResolver`；`Combat` 维持现有 SkillEntry→Route→Graph。
  3. `[Lane]` 通电 Log。
- **验收**：Combat 连段仍走 Graph（`DUAL_GATE pass`）；Locomotion/Reaction 不再触发 Graph 解析。
- **本落位不做**：Reaction（受击）/Interaction 的具体接线 — 它们此时已"在车道上"但具体支柱接线列为后续切片 OPEN；GraphParticipation 字段。

### Landing 4/4 — GraphParticipation + 空中战斗验收（融合 157.3 核心）

**目标**：把 JumpLoop / JumpLand 等 Locomotion Action 引入 Graph 作为**上下文来源节点**，使 `JumpStart → JumpLoop → DownSlash → JumpLand → Run` 全链路可在 Graph 编辑器表达、运行时严格一致执行；落地后无需为基础移动配置任何无意义 Graph 边。

- **设施**：`GraphParticipation` 枚举、`ActionDataSO.GraphParticipation` 字段（默认按 IntentCategory 派生）、Graph 求值器对 SourceOnly 目标的免审分支、JumpStart/JumpLoop/JumpLand/DownSlash 示例资产 + Graph 边 `JumpLoop→DownSlash`。
- **WIRE**：
  1. **字段就位**：`ActionDataSO.GraphParticipation` 加字段；`OnValidate` 按 IntentCategory 自动填默认值（Combat→Full、Locomotion→SourceOnly、Reaction/Interaction→None），策划可在 Inspector 显式覆盖。
  2. **求值器免审分支**：Graph 求值器在求值边时，先检查 `edge.Target.GraphParticipation`：若 `!= Full`，跳过双闸门（不做 Cost/CD/Flow/Interrupt 二次校验），直接以"已派生"结果放行。本质等价于"该节点不在 Graph 审批面内"。
  3. **示例资产链路**：
     - JumpStart / JumpLoop / JumpLand：`IntentCategory=Locomotion`，`GraphParticipation=SourceOnly`（自动派生），出现在 Graph 编辑器但 Graph 不闸门它们的进入。
     - DownSlash：`IntentCategory=Combat`，`GraphParticipation=Full`，由 Graph 编辑器画一条 `JumpLoop → DownSlash` 边。
     - JumpLand 后摇窗口：`InterruptibleByCategories |= Locomotion`（沿用 L2 模式）。

- **验收**（必须全部通过）：
  - **V4.1**：JumpStart 起跳 → JumpLoop 空中持续 → 此时按 Attack 意图 → Graph 求值边 `JumpLoop→DownSlash` 命中 → 切 Action 状态播 DownSlash（**不需要**为 JumpLoop 本身配置 Graph 进入边）。
  - **V4.2**：DownSlash 落地 → JumpLand → 后摇期 WASD → 立即转 Run（`allow=true cat=Locomotion`）。
  - **V4.3**：从未配置 `Run → JumpLoop`、`JumpStart → JumpLoop` 等 Locomotion 之间的 Graph 边，但整链路仍然顺畅可达（证明 SourceOnly 节点不要求 Graph 进入边）。
  - **V4.4**：Graph 编辑器中能看到 JumpStart / JumpLoop / JumpLand 节点（SourceOnly 与 Full 视觉差异，如颜色标）+ 边 `JumpLoop→DownSlash`；图上定义与运行时行为严格一致。
  - **V4.5**：`grep` 任何 `LocomotionTag` / `if(isLocomotion) skipGraph` / `BypassGraph` / 动作名特判命中数 = 0。

- **本落位不做**：WallRun / AirDash / LockOnStrafe 等扩展节点资产配置（设施已支持，留作后续内容切片）；Graph 编辑器对 SourceOnly 的特殊 UI 美化（仅最小可视化差异即可）；显式覆盖默认派生的 Auto/Nullable 哨兵（见开放决策点 4）。

## 十、开放决策点（请确认后我再施工 Landing 1）

1. **B 轴新增 `Locomotion` 位** vs 复用现有 `Movement` 位表达「WASD 可断」？
   （建议：新增 `Locomotion`，把 WASD/Jump 归 Locomotion，`Movement` 留给翻滚/突进等战斗位移——更贴近 157.1。）
2. **Jump 是否从 `Movement` 改判为 `Locomotion`**？（157.1 明确「Jump 属于 Locomotion」。改后需复核现有窗口是否依赖 Movement 允许 jump-cancel。）
3. **Move 意图入队的触发条件**：仅「Action 后摇期 + 移动边沿」，还是「整个 Action 期」？（建议仅后摇期产生意图，避免前摇被走路打断。）
4. **GraphParticipation 默认派生规则是否锁死**（Combat→Full、Locomotion→SourceOnly、Reaction/Interaction→None）？是否引入 `Auto` 哨兵值表达"未显式设置"？
   （建议：枚举加 `Auto = -1` 作默认值，`OnValidate` 仅在 `Auto` 时按 IntentCategory 派生；策划显式选 Full/SourceOnly/None 即覆盖。这样可在 Inspector 一眼看出"是否被人改过"。）
5. **Graph 求值器对 SourceOnly 节点是否完全免审，还是仍要过 Cost/CD 但跳过 Flow/Interrupt 双闸门**？
   （建议：**完全免审** —— SourceOnly 的语义就是"该节点的进入由其他系统（Locomotion / Airborne 支柱）权威负责，Graph 不再二次校验"。Cost/CD 本就只在 Combat 路径有意义。）
6. **Graph 编辑器是否需要给 SourceOnly 节点不同视觉样式**（如淡色/虚线边框）？
   （建议：最小可视化差异即可（一个颜色标），不做大面积 UI 改动。后续可与"Action Flow Graph"改名一并升级。）
7. **CombatGraph 是否在 L4 后概念改名为 "Action Flow Graph"**（157.3 提议）？
   （建议：**先不改类名**（避免触发全项目 grep/重构）；只在文档与 Inspector 标签层面渐进引入"Action Flow"措辞，类型保持 `CombatFlowGraph` 名以避免双轨期。）
