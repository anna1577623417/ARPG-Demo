# 173.1.B【精讲】RotationGate 永久续期 BUG —— 程序员教训 + AI 落位方法论

> 现象：移动方向角色不变向，没有动画响应
> 根因：`InputContextResolver.TickMoveContext` 把 "0.1s 一次性窗口" 实现成 "hasMove 期间每帧续期" → 永久压制 Locomotion 转向
> 修复：按下沿开窗，持续按住不续期；窗口过期自然释放
> 探针：单一开关 `Debug Rotation Gate` + 单一前缀 `[RotGate]` + 仅在闸门翻转时输出

---

## §1 BUG 反推：一个字段为什么能瘫痪整个 Locomotion

### §1.1 链路上的"一票否决"

```
SetLoadoutHasDirectionalModifier(true)   ← Loadout 含任何 EnableDirectional 技能就 true
        ↓
TickMoveContext 每帧续期 _contextSuppressUntil = now + 0.1s
        ↓
ShouldSuppressLocomotionRotation() == true
        ↓
┌──────────────────────────────────────────┐
│ Player.MoveByLocomotionIntent            │  ← 跳过 LookAtDirection
│ PlayerLocomotionState.OnLogicUpdate      │  ← 跳过 TurnResolver.Tick
└──────────────────────────────────────────┘
        ↓
角色不转向 + 没动画响应
```

**关键认识**：转向被两个独立路径都查同一个 gate，**一个 gate 错就两条路径全断**。这是 "Single Source of Truth" 的副作用——单一来源出错时影响范围反而最大。

### §1.2 续期 vs 一次性窗口的语义鸿沟

原代码（错）：
```csharp
if (hasMove) {
    if (!_moveActive) { _moveActive = true; ... }   // 上升沿做一些事
    _contextRotationSuppressed = true;
    _contextSuppressUntil = now + 0.1s;             // ★ 每帧续期
    return;
}
```

**程序员的常见心理误差**：写 `if (hasMove)` 时大脑默认想的是"按下的那一刻"，但代码实际执行的是"按下后每一帧"。这种语义上的"按下" vs "持续按住"的混淆是 input 类 BUG 的高发区。

修复后（对）：
```csharp
if (hasMove) {
    if (!_moveActive) {
        _moveActive = true;
        _contextRotationSuppressed = true;
        _contextSuppressUntil = now + 0.1s;         // ✓ 仅按下沿开窗
    } else if (_contextRotationSuppressed && now > _contextSuppressUntil) {
        _contextRotationSuppressed = false;         // ✓ 窗口过期自然释放
    }
    return;
}
```

## §2 程序员教训（5 条）

### §2.1 "短暂窗口" 三种实现形态，必须先想清

| 形态 | 何时用 | 代码模式 |
|---|---|---|
| **一次性窗口（Latch）** | 等待组合输入 / 容错窗口 | 上升沿 set，过期 unset |
| **持续压制（Hold）** | 按住期间始终压制 | 每帧 set，松开 unset |
| **续期窗口（Refresh）** | 心跳保活 | 每次活动续期，超时清空 |

**173.1 应是 Latch，写成了 Refresh**。**下笔之前必须先口述出 "这是 Latch / Hold / Refresh 中的哪一种"**。

### §2.2 "Edge-Triggered" 必须显式表达

涉及输入语义的代码，所有"按下" / "松开" / "进入" / "离开"等**边沿**必须用 `!_lastX && curX` 模式显式表达；不允许用"循环里 if(curX)"代替"上升沿"。

### §2.3 "永远不可能为假"的 gate 一定是 BUG

如果某条件分支永远走不到 else，那要么 gate 写错，要么这个 gate 根本不该存在。设计时要问自己：**"在什么条件下，suppressed 会变回 false？"** 如果答不上来，就是无限压制。

### §2.4 影响面广的"统一闸门"要有 watchdog

`ShouldSuppressLocomotionRotation()` 被多处调用。这类 gate 要有：
- **超时熔断**：连续 N 秒压制 + 有移动输入 → Console 告警
- **状态可视**：Inspector 直接看到 `suppressed / winLeft / reason`
- **可强制释放**：Debug 面板加 "Force Clear" 按钮

### §2.5 "一次性引入多个系统" 是头号风险源

本次 BUG 出现的真实背景是 "近期一次性引入了多个系统但没来得及验证"。
- **新系统单独提交、单独验证**
- 多系统并入时跑一遍 **smoke test 矩阵**：站桩、移动、转向、攻击、跳跃、复活，每项目视一次
- 用 git bisect 心态切片：**这次 BUG 是 173.1 引入的，单独提交本可 10 秒定位**

## §3 AI 落位方法论（6 条 —— 给后续 AI 协作者）

### §3.1 "三层模型先于代码"

写功能性逻辑前，必须先在注释里**口述三层**：

```csharp
// 【语义】WASD 按下后等方向技能键的 100ms 组合窗口
// 【形态】Latch — 上升沿开窗，过期或松开后自然释放
// 【边界】窗口期间 → suppress 转向；非窗口期 → Locomotion 接管
```

这三行写得出来，下面的代码就基本不会错；写不出来，代码 100% 出 BUG。

### §3.2 "Gate 必须可证伪"

每加一个 `if (suppressed)` 分支，必须能回答：
- ❓ **谁让它变 true？**（按下沿 / 显式 Commit）
- ❓ **谁让它变 false？**（窗口过期 / 松开 / 显式 Clear）
- ❓ **两条路径之间是否可达？**（有无死锁）

若任意一项答不上来，gate 即 BUG 候选。

### §3.3 "一对一探针 7 字诀"（本次实践）

> **一开关 / 一前缀 / 翻转打**

| 元素 | 规则 |
|---|---|
| **一开关** | Inspector 独立 bool，禁止混 `DebugLocomotion` 等大杂烩 |
| **一前缀** | `[RotGate]`、`[Combat][Finisher]` 等独占标签，Console 过滤一键到位 |
| **翻转打** | 仅在状态翻转时输出一行（dedup by last state），同状态期间静默 |
| **上下文齐** | 一行内含全部判定字段：source / target / winLeft / frame |
| **可关掉** | 默认 false；发布前 grep 一次确认无遗留 true |

**反模式（必须避免）**：
- ❌ 每帧打（哪怕 dt 小也是刷屏）
- ❌ 多 BUG 共用一个开关（"Debug Everything"）
- ❌ 缺 dedup（同事件重复触发也重复打）
- ❌ 信息量碎（一条只有一个字段，要拼三行才看懂）

### §3.4 "静态修复 → Log 探针 → 动态验证" 三步走

正确顺序：
1. **静态排查**：grep 调用链、读 gate 翻转条件、找出嫌疑点
2. **打探针 + 给最小修复**：探针仅供"修没修好"二判，不参与定位
3. **用户跑一次 → 看探针 → 决定下一步**

错误顺序（应严格避免）：
- ❌ 不读代码直接堆探针 → 探针太多反而干扰
- ❌ 不修就交付探针 → 用户负担 + 心理预期落空
- ❌ 修了一堆地方 → 难以定位真正生效的改动

### §3.5 "改动半径" 最小化

本次修复涉及：
- `InputContextResolver.cs`：核心 5 行（续期 → 边沿）+ 探针字段 / 方法
- `Player.cs`：1 个 SerializeField + 1 个同步方法 + OnValidate

**改动半径足够小** = 万一修错可秒级回滚；同时改动**只在 BUG 路径**，不顺手"清理"无关代码。

> "顺手优化"在 BUG 修复 PR 里是禁区 —— 它把"是否修好"这个二元问题变成"哪个改动让它好的"四象限。

### §3.6 "总结沉淀到 KB" 是协作闭环的最后一公里

修复完成后必须：
- 写一份 `170.4` / `173.1.B` 这类**精讲文档**到 KB 对应目录
- 文档**只讲根因 + 误诊 + 正解 + 方法论**，不重复贴代码
- 给未来的人（或 AI）留 grep 锚点：`[RotGate]` / `173.1.B FIX` 等关键串

下次同类 BUG 出现时，文档秒级定位，节省 10-100 倍排查时间。

## §4 通用反模式清单（这次 BUG 暴露的）

| 反模式 | 表现 | 防御 |
|---|---|---|
| **每帧续期当作短窗口** | `if (active) { until = now + win; }` 写在循环里 | 改为 `if (!wasActive && active) until = now + win;` |
| **gate 单向可达** | suppressed 只有 true 路径，无 false 路径 | 显式写 release 分支 + 单元测试 "gate 必能翻 false" |
| **多个 BUG 一个 Debug 开关** | `if (debugSomething)` 包了 200 条 Log | 一开关一前缀，按 BUG 隔离 |
| **静默 fallthrough** | Loadout 配置改 → 隐式触发 modifier=true → 行为剧变 | 任何隐式配置触发都要有 Log 边界事件 |
| **新功能 = 一次性多系统** | 173.1 一次性引入 InputContext + RotationArbitration + DirectionalCommit | 拆 PR，每个独立验证；CI 跑 smoke 矩阵 |
| **Log 信息密度过低** | "[RotGate] suppressed=true" 一行只有一个字段 | 一行打全字段 owner/policy/winLeft/frame，相对时间戳 |

### §5.2 翻转输出

```csharp
void LogXXXIfFlipped(float now)
{
    if (!DebugXXXGate) return;
    if (_currentGateState == _lastXXXLogged) return;
    _lastXXXLogged = _currentGateState;
```

只在 **gate 翻转点** 调；不在 Tick 末尾盲调。
